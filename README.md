# i-Retail Coffee One Love

Текущая рабочая версия: **0.5.55-s3-dry-run-v2**.

Android-проект теперь расположен непосредственно в корне репозитория. Дополнительный каталог
`iRetail_Android_UI_v0.5.8_smartskypos_probe_source` больше не используется.

## Структура

Основные каталоги:

- `app/` — основное Android-приложение i-Retail;
- `kozenBridge/` — мост Kozen / SmartSkyPOS;
- `kozenRecoveryBridge/` — безопасное восстановление состояния платежей;
- `jl22AoaProbe/`, `jl22AoaRecovery/` — диагностические приложения JL22;
- `docs/` — контракты, отчёты и история исследований;
- `tools/` — проверочные и служебные сценарии;
- `test_reports/` — сохранённые результаты испытаний;
- `.github/workflows/` — автоматические проверки и сборки.

## Сборка под Windows

Из корня репозитория:

`BUILD_WINDOWS_CLI.bat`

Сценарий собирает debug APK и сохраняет копию в `dist/`.

## Контрактный этап S1

В версии 0.5.34 был завершён первый программный этап S1:

- неподтверждённые способы оплаты не объявляются успешными;
- подтверждённый Kozen-платёж отделён от фискализации;
- локальный суррогат фискального чека удалён;
- выдача, стакан и разогрев не возвращают фиктивный успех;
- таймеры не завершают оплату или выдачу вместо реального результата.

Версия 0.5.35 перенесла проект в корень репозитория. Версия 0.5.36 реализует S2: точные суммы в копейках и безопасную замену кэша каталога только после проверки новой выгрузки. Версия 0.5.37 добавляет только локальный безопасный черновик будущего заказа без сетевой отправки. Версия 0.5.38 провела живую приёмку: S3 DRY_RUN принят, а S2 не получил живой ZIP и ушёл на content XML. Версия 0.5.39 добавляет безопасную диагностику причины отказа живого каталога. Версия 0.5.40 добавила независимую Windows/curl-проверку документации, авторизации и загрузки каталога теми же вызовами, что использует Android. Версия 0.5.41 исправляет обнаруженную при первом живом запуске ошибку PowerShell при вычислении размера файлов документации. Версия 0.5.42 локализовала отказ JL22 до этапа SSL при авторизации. Версия 0.5.43 уточняет тип SSL-сбоя и безопасно собирает сведения о времени, доверенных CA и TLS-окружении Android 6 без отключения проверки сертификатов. Версия 0.5.44 добавила безопасный TLS chain probe, версия 0.5.45 исправила захват CHAIN/CERT, версия 0.5.46 закрыла S2 живой загрузкой каталога через точечную совместимость Android 6 с ISRG Root X1, версия 0.5.47 начала read-only аудит актуального серверного контракта заказа S3, версия 0.5.48 исправила конфликт имени `Curl` со встроенным псевдонимом Windows PowerShell `Invoke-WebRequest`, версия 0.5.49 собрала read-only документацию зависимостей `device/shift/employee/operation/payment/offer/reference`, а версия 0.5.50 получила живые read-only справочники и выявила, что configured device_id=6287 не определяется сервером как касса; версия 0.5.51 начала read-only сверку реальных устройств канала и платёжных служб, версия 0.5.52 исправила несовместимый с Windows PowerShell 5.1 способ помещения Generic.List в SUMMARY, версия 0.5.53 устранила ложное срабатывание общего safety scan, а версия 0.5.54 усиливает санитизацию публичных диагностических отчётов: любые поля token/password/secret теперь редактируются по суффиксу ключа, а лишние account/user identifiers не публикуются. Версия 0.5.55 перестраивает локальный S3 DRY_RUN под доказанную структуру order/synchronize и оставляет недоказанные device/shift/counters и поля жизненного цикла незаполненными.

## Проверки

Перед каждой автоматической Android-сборкой выполняются:

1. проверка корневой структуры 0.5.35;
2. проверка инвариантов S1;
3. проверка S2 по каталогу и денежной точности;
4. проверка безопасного черновика S3;
5. проверка диагностического выпуска 0.5.39;
6. проверка Windows/curl-аудита 0.5.41;
7. синтаксическая проверка PowerShell;
8. `assembleDebug`.

## Важное

- минимальная версия Android основного приложения — API 23 / Android 6;
- финансовые операции не должны автоматически повторяться после неопределённого результата;
- wire-протоколы SmartSkyPOS и Vendotek нельзя менять без отдельного согласования;
- Multicard на текущем этапе не интегрируется.


## Проверка живого каталога

Для проверки реального обмена с I-Retail на Android используется:

`S2_01_BUILD_INSTALL_CATALOG_AUDIT.bat`

Сценарий собирает и устанавливает APK, запускает приложение, ждёт обновления каталога и формирует ZIP-отчёт в `test_reports\s2_catalog\`. Успешная сборка сама по себе не считается доказательством доступности живого API.


## Объединённая приёмка S2 + S3

Для одного безопасного живого прогона используется:

`S23_01_BUILD_INSTALL_ACCEPTANCE_AUDIT.bat`

Сценарий собирает и устанавливает APK один раз, ждёт обновления каталога, затем просит добавить товары и открыть экран способов оплаты. Выбирать способ оплаты не нужно и нельзя: финансовая операция в этом тесте не требуется.

Результат сохраняется в `test_reports\s23_acceptance\S23_ACCEPTANCE_*.zip`.


## Диагностика отказа живого каталога

Живой отчёт v0.5.38 показал `success=false source=content XML`, поэтому S2 пока не принят.

Для следующего безопасного прогона используется:

`S2_02_CATALOG_DIAGNOSTICS.bat`

Сценарий:
- сам ищет JL22 по полной ADB-сигнатуре `product:octopus_jetinno model:UniWin_M190 device:octopus-jetinno`;
- если однозначного совпадения нет, показывает нумерованный список Android-устройств и просит выбрать устройство;
- даже единственное найденное устройство проверяется по сигнатуре;
- собирает и устанавливает APK;
- не включает реальный POS;
- фиксирует безопасный этап и причину отказа каталога без секретов.

Для загрузки последнего отчёта в Git используется:

`S2_03_PUBLISH_LATEST_DIAGNOSTICS.bat`


## Независимая Windows/curl-проверка Retail API

Для проверки API напрямую с Windows, без Android и ADB:

`RAPI_01_FETCH_DOCS_AND_TEST_CATALOG.bat`

Сценарий автоматически:

1. сохраняет текущую документацию `my.i-retail.com/api/apidoc/actual`;
2. выполняет авторизацию тем же форматом запроса, что Android;
3. выполняет загрузку каталога тем же маршрутом и набором полей;
4. сохраняет безопасный отчёт;
5. проверяет отчёт на утечку учётных данных;

Отдельный повтор публикации последнего отчёта:

`RAPI_02_PUBLISH_LATEST_API_AUDIT.bat`

Сырое тело авторизации и access token в Git не попадают.

## Текущий следующий шаг — приёмка ISRG Root X1

TLS-chain probe доказал цепочку `YR1 → Root YR → ISRG Root X1`, которую штатный Android 6 не принимает.

Версия 0.5.46:
- сохраняет обычное системное доверие;
- при системном отказе добавляет официальный ISRG Root X1;
- применяется только к `my.i-retail.com` на Android 6;
- не отключает проверку имени узла.

Живая проверка:

`S2_02_CATALOG_DIAGNOSTICS.bat`

Успех S2: `REFRESH success=true source=I-Retail ZIP`.

## S3 — аудит серверного контракта заказа

После закрытия S2 реальная отправка заказа по-прежнему не включается, пока не подтверждён актуальный wire-контракт I-Retail.

Для получения документации используется:

`S3_02_FETCH_ORDER_API_DOCS.bat`

Сценарий:
- скачивает актуальный `api/apidoc/actual/index.html`;
- сам находит страницы контроллеров заказа;
- сохраняет найденные страницы;
- отмечает упоминания `reserve-order-id`, `synchronize`, `employee_id`, `pin`, `offer_id`, `quantity`, `price`, `idempotency` и других полей;
- выполняет только GET документации;
- не создаёт и не синхронизирует заказ;
- автоматически публикует ZIP-отчёт в Git.


## S3 — связанные поля заказа

Аудит `order/synchronize` показал, что прежний DRY_RUN слишком упрощён для сетевой отправки.

Следующий read-only шаг:

`S3_04_FETCH_ORDER_DEPENDENCY_DOCS.bat`

Сценарий скачивает только HTML-документацию связанных контроллеров, ищет источники `employee_id`, `shift_id`, статусов, `service_in_slug`, счётчиков, нумерации заказа и товарных полей, затем автоматически публикует ZIP в Git.

Реальная синхронизация заказа остаётся отключённой.


## S3 — живые read-only справочники

Для получения фактических серверных значений без создания заказа используется:

`S3_06_FETCH_LIVE_REFERENCE_DATA.bat`

Сценарий:
- авторизуется тем же безопасным способом, что каталог;
- читает статусы заказа/оплаты, типы операций, валюты и типы товаров;
- читает список входящих платёжных служб;
- читает текущую активную смену;
- читает сотрудников канала с удалением имён и PIN из отчёта;
- читает безопасные сведения об устройстве;
- читает налоговые ставки профиля;
- удаляет токены, секреты, PIN, коды устройства, телефоны/e-mail и персональные имена из сохраняемых данных;
- автоматически публикует ZIP в Git.

Сценарий **не вызывает** `order/synchronize`, `device/register`, открытие/закрытие смены, `employee/authorize` или `payment-in/create`.


## S3 — сверка устройства и платёжных служб

Следующий read-only шаг:

`S3_08_RECONCILE_DEVICE_SERVICE.bat`

Сценарий:
- читает канал;
- получает реальные устройства текущего канала;
- для каждого найденного устройства (не более 20) читает device-info и активную смену;
- проверяет, присутствует ли configured device_id среди устройств канала;
- получает настроенные и использованные платёжные службы профиля;
- не выбирает устройство автоматически;
- не регистрирует устройство;
- не открывает/закрывает смену;
- не авторизует сотрудника по PIN;
- не создаёт платёж;
- не отправляет заказ;
- удаляет секреты и персональные данные из публикуемого отчёта.

После этого можно построить DRY_RUN v2 только из доказанных device/service/shift значений.


## S3 — безопасная повторная сверка после очистки отчёта

В v0.5.54 повторно используется:

`S3_08_RECONCILE_DEVICE_SERVICE.bat`

Сетевой набор вызовов остаётся read-only. Изменена только защита отчёта:
- любые поля, оканчивающиеся на `token`, `password`, `secret`, скрываются;
- дополнительно не публикуются лишние идентификаторы аккаунта/пользователя;
- независимый ZIP-контроль блокирует публикацию при обнаружении неотредактированных чувствительных полей.

После чистого повторного отчёта можно продолжать DRY_RUN v2.


## S3 — DRY_RUN v2

Версия 0.5.55 не включает сетевую отправку заказа. Локальный черновик теперь повторяет документированную оболочку `order/synchronize`:

- `device_id`;
- `counters`;
- `shift`;
- `orders`;
- `operations`.

Текущие device/shift/counters не доказаны, поэтому в wire-кандидате остаются `null`. Старые device 3476 / shift 164570 сохраняются только как read-only evidence и не используются для нового заказа.

Живой безопасный прогон:

`S3_10_BUILD_INSTALL_DRY_RUN_V2_AUDIT.bat`

Сценарий собирает и устанавливает APK, просит только добавить товар и открыть экран способов оплаты, извлекает локальный JSON, проверяет его и автоматически публикует безопасный ZIP.

Запрещённые действия остаются запрещены: `device/register`, `order/synchronize`, изменение смены, авторизация сотрудника и создание платежа.

После живого DRY_RUN v2 следующий контрактный вопрос — можно ли использовать штатный `device/register(device_code)` как источник актуальных device/counters/shift.
