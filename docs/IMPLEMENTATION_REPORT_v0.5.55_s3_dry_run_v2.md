# Отчёт реализации v0.5.55 — S3 DRY_RUN v2

## Цель

Построить максимально точный локальный кандидат `order/synchronize` из доказанных данных, не меняя состояние I-Retail и не выдумывая отсутствующие значения.

## Результат

DRY_RUN v2 теперь отражает фактическую опубликованную структуру synchronize и отделяет три класса данных:

1. **wire-кандидат** — только документированные поля;
2. **доказанные read-only сведения** — канал, валюта, товарные метаданные, налог, сотрудник-кандидат, карточная служба-кандидат, исторический device/shift snapshot;
3. **блокеры** — всё, что нельзя безопасно считать текущим значением.

Критические поля текущего устройства, смены и счётчиков в wire-кандидате остаются `null`.

## Безопасность

`OrderSyncDraftBuilder` не содержит HTTP-клиента и не выполняет сетевых действий. Живой сценарий только:

- собирает и устанавливает APK;
- создаёт локальный черновик через обычный интерфейс;
- читает файл через ADB `run-as`;
- проверяет JSON;
- пакует и публикует диагностический ZIP.

## Проверки

Добавлены:

- общий программный guard `tools/verify_s3_order_draft.py`;
- guard выпуска `tools/verify_v0_5_55_s3_dry_run_v2.py`;
- ZIP-проверка `tools/Assert-S3DryRunV2Safe.ps1`.

Автоматическая сборка должна дополнительно подтвердить компиляцию Android-проекта.

## Прогресс S3

План S3 на текущем рубеже: 5 шагов.

1. Аудит `order/synchronize` — готово.
2. Аудит зависимостей и живых справочников — готово.
3. Сверка устройства/смены/платёжных служб — готово.
4. DRY_RUN v2 — программно готов; нужен живой прогон.
5. Контрактное решение по источнику актуальных device/counters/shift и последующая безопасная интеграция — не выполнено.

После программной реализации: **4/5, 80%**, но шаг 4 считается закрытым только после живого ZIP с JL22.
