# DELTA v0.5.43 — уточнение SSL-сбоя JL22

Дата: 20.09.2026  
Основа: живой отчёт `S2_DIAGNOSTICS_20260920_145440.zip`.

## Доказано на v0.5.42

JL22 определён по полной ADB-сигнатуре:
- `product:octopus_jetinno`;
- `model:UniWin_M190`;
- `device:octopus-jetinno`.

Устройство:
- Android 6.0.1;
- DNS: 8.8.8.8 / 8.8.4.4;
- `my.i-retail.com` разрешается в адрес и отвечает на ping;
- HTTP proxy отсутствует.

Приложение падает до ответа API:
- `failureStage=authentication`;
- `failureReason=SSL`.

При этом Windows/curl на тех же учётных данных успешно получает:
- HTTP 200 на авторизацию;
- access token;
- HTTP 200 + application/zip на каталог.

## Цель v0.5.43

Не менять доверие TLS и не обходить проверку сертификатов. Только различить класс SSL-сбоя и безопасно собрать сведения об окружении Android 6.

## 🟢 Добавлено

- отдельные причины:
  - `SSL_HANDSHAKE`;
  - `SSL_PEER_UNVERIFIED`;
  - `SSL_PROTOCOL`;
  - `SSL_KEY`;
  - `SSL`;
- `failureDetail` — цепочка **только имён классов исключений**, без текстов исключений и секретов;
- время JL22 в UTC;
- часовой пояс;
- состояние автоматической установки времени;
- уровень security patch;
- количество системных CA-сертификатов;
- наличие системных `curl/wget/openssl`, если они есть.

## 🟡 Изменено

- версия: `0.5.43-s2-jl22-ssl-diagnostics`, `versionCode 43`;
- диагностический ZIP содержит расширенные безопасные признаки TLS-окружения.

## 🔴 Не добавлено

- нет доверия всем сертификатам;
- нет отключения hostname verification;
- нет собственного permissive TrustManager;
- нет HTTP вместо HTTPS;
- нет изменений серверных маршрутов/полей.

## Критерий следующего решения

Исправление TLS выбирается только после живого отчёта v0.5.43. До этого нельзя безопасно решить, нужен ли:
- современный TLS provider;
- дополнительный доверенный корень;
- исправление времени;
- исправление цепочки сертификатов на сервере;
- иной точечный вариант.
