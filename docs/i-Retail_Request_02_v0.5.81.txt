Интегрирую приложение Coffee One Love (это наше кодовое название приложения i-Retail) с i-Retail для самообслуживаемой кофейной точки.

Наши идентификаторы:
✔️ profile_id: 2512
✔️ channel_id: 5676
✔️ текущая coffee_machine: device_id 3476

Сценарий работы:
1️⃣ Android-приложение работает непосредственно на кофемашине Jetinno JL22;
2️⃣ пользователь выбирает напиток;
3️⃣ оплата проходит через внешний POS-терминал;
4️⃣ после достоверного подтверждения оплаты приложение должно передать заказ в i-Retail и обеспечить его фискализацию;
5️⃣ приготовление кофе запускается отдельным контуром.

Сейчас через iretail/device/get-by-channel-id видна только coffee_machine 3476.

Я проверил оба документированных способа регистрации этой coffee_machine:
✔️ device/register(device_code);
✔️ device/register-external-system(external_code).

Оба запроса сервер принял по HTTP, но вернул status=false; новых устройств не появилось.

В документации i-Retail методы register/register-external-system возвращают device с type_slug workplace_cashier или self_service_terminal. Также в актуальной API-документации есть отдельный admin/device/create для создания устройства.

Административного доступа у меня нет: обычная user/authentication работает, а user/admin-authentication с теми же реквизитами возвращает status=false. Текущий user/get-permissions возвращает только right.managementOrderRefund.

При этом в переданной ранее документации я нашёл ещё один важный контур — «Протокол обмена данными с внешними сервисами — потребителями фискализации заказов». В нём описаны:
➡️ /api/cloud-fiscal/order/create;
➡️ /api/cloud-fiscal/order/getStatus;
➡️ callback с результатом фискализации и invoice_url.

Этот API авторизуется через api_key + login и, судя по документу, не требует во входном запросе device_id, counters и shift.

Документ старый (2019 год), поэтому прежде чем что-либо внедрять, хочу уточнить актуальную штатную схему.
