# i-Retail 0.5.128 — привязка устройства и первый запуск

Дата: 26.09.2026. Ветка: `v0.5.128-device-binding`.
Основа: `58622dcbb7de6dfcc7a622522fc5878bd10a7cad` (0.5.127).
Проверенный прикладной код: `e93a332437cb3953dd0dc26a5770993673f67bcd`.

## Результат и граница готовности

Реализован нативный мастер Android 6: авторизация, одна управляемая активация, проверка возвращённых идентификаторов, зашифрованное сохранение, загрузка своей конфигурации/каталога и запрет покупательского режима до готовности. Это проверочная API-версия, не сообщение об успешной активации настоящей JL22.

Финансовые операции, отправка продаж, смены, телеметрия и приготовление в этой работе не выполнялись. Настоящую активацию запускает оператор на JL22 после подтверждения в мастере. Платёжные исполнители в этом выпуске дополнительно закрыты независимо от сохранённого ранее `real_pos_enabled`.

## 2. Инцидент диагностического PIN

Мой первоначальный фильтр технических ответов пропустил поле `code`, которое сервер устройства использует для активационного PIN. Код оказался в созданном мной журнале GitHub Actions и вложении. Это ошибка фильтрации.

Запуск `36253752452` удалён целиком вместе с журналом и вложениями; удаление выполнено запуском `36253870872`. Отсутствие чужого чтения до удаления не установлено. **Прежний PIN считать раскрытым и перевыпустить в ЛК до активации.** Удаление журнала не отзывает код. Код в запрос регистрации не отправлялся.

Новый PIN вводится только на JL22, его не нужно пересылать в чат. Новый отчёт Windows не переносит произвольные API-поля: он строится из закрытого набора состояний, числовых ID и логических признаков. Поле `code`, сырой JSON, пароль, client_secret, снимки полей ввода и файл привязки в него не входят.

## 3. Реализация

### Первый запуск и ограничения

MainActivity до сетевых/покупательских сценариев проверяет запись установки и при отсутствии готовности открывает неэкспортируемую DeviceBindingActivity. Проверки стоят также в репозитории, создании локального заказа и карточном исполнителе. Старый сохранённый каталог и вручную прописанные ID не являются привязкой. Технику доступны сеть и безопасный статус.

### Активация и неизвестный результат

Оператор вводит логин/пароль ЛК, ID устройства, новый PIN, client_id и client_secret из раздела 2.2 личного реестра. Платёжные ключи, AnyDesk и локальный токен Jetinno здесь не используются. Публичный client_id начально заполнен как IRETAIL_TERMINAL; рабочие секреты в APK отсутствуют.

Перед регистрацией чтением проверяются выбранный ID, его канал и тип. В `device_code` используется точное историческое преобразование TSO: нижнерегистровая MD5-сумма от PIN с добавленной протокольной константой. Это совместимость формата, не алгоритм хранения паролей. Нынешняя документация называет поле `Encrypted code for device`, не раскрывая формулу. Подтверждение успешной регистрации нового устройства остаётся частью живой приёмки; альтернативные преобразования не перебираются.

Состояние REGISTERING записывается до сетевой отправки. Успешный ответ целиком сохраняется зашифрованным до разбора; затем проверяются device_id, device_inner_id, channel_id и type_slug. Счётчики/смена из ответа не теряются, отсутствующие значения не выдумываются.

Потеря ответа, повреждённый успех, перезапуск или утрата ключа не разрешают автоматический повтор PIN. При явном отказе следующую попытку инициирует оператор. После стадии BOUND кнопка повторяет только загрузку настроек, а не регистрацию.

### Настройки и кэш

Канал/профиль/валюта и рабочие реквизиты берутся из сохранённой привязки, а не старого content/iretail-api.json. Каталог изолирован по серверу, установке, устройству, каналу и профилю; старый глобальный кэш не подставляется. Запись применяет AtomicFile, fsync, проверку кандидата и синхронизацию файловых операций.

Готовность требует успешной загрузки каталога и списка служб. Явно пустой массив товаров допустим; неполный или неизвестный ZIP не считается пустым. Ошибка каталога новой точки не удаляет привязку и не требует повторной активации. Служба использует `settings.enable`, не атрибут `enabled` старого XML. Финансовый исполнитель не включается от одного присутствия службы.

### Сохранение и переход

Реквизиты и результат находятся в зашифрованном AtomicFile внутри noBackupFilesDir. AES-GCM, случайный IV, Android Keystore, проверка целостности. Нет открытого запасного файла или автоматической замены отсутствующего ключа существующей записи. Экран ввода имеет FLAG_SECURE; поля не сохраняют секреты в состоянии представлений.

Пароль/client_secret и старые ID удалены из рабочего конфигурационного ресурса и значений по умолчанию. Это не чистка истории Git и не смена ранее опубликованных реквизитов. Ротация согласуется отдельно.

Старые журналы, кэш и платёжные маркеры не стираются. Незавершённая прежняя операция блокирует привязку. Автоматическая смена уже настроенной точки и восстановление после неизвестной активации ещё требуют отдельной процедуры; кнопки «стереть и повторить» нет.

## 4. Проверки

Подготовительная проверка выполнила 26 новых DeviceBindingTest и 10 ApiLifecycleSafetyTest: 0 ошибок, отказов и пропусков. Собраны app и kozenBridge, после проверки опубликован прикладной код e93a3324. Тестовые реквизиты вымышленные; транспорт подставной, живые API не вызываются.

Покрыты: первый запуск, PIN/ID, ведущий ноль, отказ авторизации, несовпадение устройства/канала, запись до отправки, ошибка диска, потеря ответа, повтор после перезапуска, сохранение успешного ответа и счётчиков, валютная проверка, частичная загрузка, разделение кэша и запреты операций.

Постоянный Device binding safety повторяет JVM-тесты и проверяет PowerShell. Его отдельный инструментальный этап предназначен только для свежего эмулятора Android 6/API23: старт мастера, ориентация, секретные поля, шифрование/чтение Keystore, случайные IV, резервная запись, повреждение и утрата ключа. Результат определяется фактически завершённым запуском; наличие кода не считается успешным тестом.

Штатный Android build остаётся отдельной проверкой совместимости прежних частей. Ни JVM-тесты, ни эмулятор не заменяют приёмку на настоящей JL22 и живую регистрацию.

## 5. Проверка на JL22

1. В ЛК перевыпустить PIN. Устройство не удалять и ID не менять ради теста.
2. Получить ветку v0.5.128-device-binding в существующем локальном репозитории. При конфликте не выполнять принудительный сброс.
3. Запустить MAIN_41_DEVICE_BINDING_SAFE_TEST.bat. Он собирает APK локально с прежним ключом подписи, выбирает устройство и требует точную сигнатуру product:octopus_jetinno model:UniWin_M190 device:octopus-jetinno. Установка — adb install -r, без очистки.
4. Несовпадение подписи — остановка, не разрешение удалить приложение. CI APK может иметь иной отладочный ключ; локальная сборка является основным путём обновления.
5. На JL22 ввести данные Retail из личного файла, ID устройства 3669 и новый PIN. Канал и профиль руками не вводить.
6. Подтвердить одну активацию. Ожидаемые по проверке ID: 3669 / 6002 / 1885, тип vending, RUB; фактический ответ сервера важнее этого датированного ожидания.
7. При сохранённой привязке и сбое настроек повторить только их загрузку. При неизвестном результате регистрации остановиться и сверить ЛК, не повторять PIN.
8. После экранного результата нажать Enter в Windows. Будет создан обезличенный JSON reports/device-binding и опубликован штатным механизмом одного артефакта. При ошибке публикации файл останется локально.
