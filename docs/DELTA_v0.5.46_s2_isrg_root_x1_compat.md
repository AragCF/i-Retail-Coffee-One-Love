# DELTA v0.5.46 — совместимость ISRG Root X1 для JL22 / Android 6

Дата: 20.09.2026  
Основа: живой TLS-chain отчёт `TLS_CHAIN_20260920_192642.zip`.

## Доказанная причина

Сервер `my.i-retail.com` предъявляет цепочку:

1. leaf: `CN=admin.beta.i-retail.com`;
2. `Let's Encrypt YR1`;
3. `Root YR`, подписанный `ISRG Root X1`.

Системный TrustManager JL22 Android 6.0.1 отвергает цепочку:

`SSLHandshakeException > CertificateException > CertPathValidatorException`.

Документация Let's Encrypt указывает:
- стандартная цепочка YR1: `EE ← YR1 ← Root YR ← ISRG Root X1`;
- штатное доверие к ISRG Root X1 на Android начинается с Android 7.1.1.

## Цель

Дать приложению на Android 6 возможность валидировать именно эту доверенную цепочку без отключения TLS-проверок.

## 🟢 Добавляется

- официальный self-signed `ISRG Root X1` из репозитория Let's Encrypt;
- проверка SHA-256 встроенного корня перед использованием;
- дополнительный X509TrustManager, который:
  1. сначала использует системное хранилище доверия;
  2. только при системном отказе пробует доверенный `ISRG Root X1`;
- совместимость применяется только:
  - на Android API <= 23;
  - для хоста `my.i-retail.com`;
- диагностический журнал `IretailTlsCompat`.

## 🟡 Изменяется

- версия приложения: `0.5.46-s2-isrg-root-x1-compat`, `versionCode 46`;
- HTTPS-соединения I-Retail на JL22 получают совместимый SSL socket factory.

## 🔴 Не изменяется

- HostnameVerifier;
- имя хоста;
- серверные маршруты и параметры API;
- учётные данные;
- логика каталога;
- денежная модель;
- платежи;
- S3 DRY_RUN.

## ⚠️ Инварианты безопасности

- нет `trust-all`;
- нет принятия произвольного сертификата;
- нет отключения проверки имени узла;
- нет HTTP вместо HTTPS;
- дополнительный корень принимается только при совпадении его SHA-256 с официальным ISRG Root X1;
- на Android 7+ используется обычное системное доверие.

## Критерий приёмки

Живой прогон S2 должен дать:
- `REFRESH success=true source=I-Retail ZIP`;
- ненулевое число товаров;
- отсутствие SSL ошибки;
- сохранение системного отказа в отдельном chain-probe допустимо и ожидаемо, потому что probe намеренно проверяет только системный TrustManager.
