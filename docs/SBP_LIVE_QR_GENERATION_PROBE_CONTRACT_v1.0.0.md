# Контракт пробного получения живого СБП-QR v1.0.0

Дата: 25.09.2026  
Статус: **PREPARED_NOT_ARMED**

## 1. Что уже доказано

Безопасный экранный СБП-контур JL22 подтверждён на реальном оборудовании:

- QR строится локально;
- телефон считывает синтетический payload;
- состояние проходит `QR_READY → WAITING → CONFIRMED`;
- восстановление сессии работает на Android 6;
- финансовый вызов в этих проверках не выполнялся.

## 2. Следующая цель

Проверить реальный источник QR в SmartSkyPOS:

`JL22 → AOA → Kozen Bridge → SmartSkyPOS qrPayment → onQrReading(qrId, payload) → AOA → JL22`.

Одновременно нужно увидеть, что показывает экран самого Kozen во время этой операции.

## 3. Почему это уже финансовая граница

Binder transaction #19 `qrPayment` создаёт реальную платёжную СБП-сессию. Даже если QR не сканировать, сам вызов нельзя считать read-only.

Поэтому реализация подготовлена, но по умолчанию физически заперта:

- `LIVE_QR_PAYMENT_ENABLED=false`;
- `LIVE_QR_GENERATION_PROBE_ENABLED=false` на Kozen Bridge;
- `LIVE_QR_GENERATION_PROBE_ENABLED=false` в JL22-контракте.

Обычная команда `QR_PAYMENT` по-прежнему жёстко блокируется.

## 4. Ограничения будущей единичной пробы

Когда проба будет отдельно разрешена, она должна соблюдать все условия одновременно:

- сумма строго 1,00 ₽;
- валюта 643;
- только свежий маршрут `type=42 / transactionType=qrPayment`;
- обязательный TID;
- SmartSkyPOS state=0;
- один requestId;
- один Binder transact #19;
- никакого автоматического повтора;
- вызов Binder выполняется в отдельном рабочем потоке, чтобы AOA оставался доступен для callback;
- QR принимается только из `onQrReading`;
- payload и qrId не пишутся в журналы;
- QR показывается на JL22 с явной надписью «НЕ СКАНИРОВАТЬ»;
- до отдельного этапа QR нельзя сканировать банковским приложением;
- заказ не становится PAID;
- фискализация не запускается;
- приготовление кофе не запускается;
- отмена, возврат и повторный qrPayment автоматически не выполняются.

## 5. Поведение при неопределённости

После попытки сохраняется устойчивый маркер незавершённой СБП-пробы.

Если ответ потерян, новый `qrPayment` запрещён. Разрешено только читать состояние уже начатой операции. Неопределённость никогда не считается успехом.

## 6. Текущий разрешённый шаг

В v0.5.121 разрешён только read-only preflight:

`MAIN_36_SBP_QR_SOURCE_PREFLIGHT.bat`

Он:

- устанавливает Bridge 0.5.7 и i-Retail 0.5.121;
- оставляет `real_pos=false`;
- читает PING / INFO / GET_STATE / GET_TERMINAL_DATA / GET_SBP_ROUTE;
- подтверждает маршрут `42/qrPayment/643`;
- подтверждает `liveEnabled=false`;
- подтверждает `probeEnabled=false`;
- не создаёт СБП-сессию и не отправляет финансовых команд.

После чистого preflight отдельным решением можно разрешить ровно одну реальную генерацию QR на 1 ₽ без сканирования.
