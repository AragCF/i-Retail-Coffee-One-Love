# PROTOCOL_iRetail_Android_UI_v0.3_bugfix_integration_contract

Статус: **кандидат на утверждение**  
Проект: **i-Retail / Android-фронт для робо-кофейни Jetinno JL22**  
Платформа: **Android 6+**  
Основной стек: **Kotlin + нативный Android UI**  
Основа: **v0.2.2, собранный Windows CLI-проект**  
Код по этому документу не пишется и не меняется до отдельного подтверждения.

Версия v0.3 фиксирует следующий шаг: **исправить найденные ошибки пользовательской логики в UI MVP, привести корзину и выбранные товары к единому источнику истины, добавить рабочую экранную навигацию без системных кнопок Android, а также приобщить новые документы и архив старого терминального приложения как справочные источники для дальнейших интеграций**.

## 1. Назначение документа

Этот контракт описывает не новый продукт с нуля, а точечное развитие уже выпущенного Android UI MVP v0.2.2.

Главная задача версии v0.3 — убрать ошибки, из-за которых приложение выглядит как статическая демонстрация экранов, а не как управляемый интерфейс заказа:

- выбранный товар должен быть именно тем товаром, по которому нажал пользователь;
- корзина должна показывать актуальное состояние, а не заранее нарисованные позиции на PNG;
- экран добавления товара должен хранить выбранные настройки;
- всплывающие окна и экранные клавиатуры должны открываться и закрываться;
- навигация должна выполняться только через элементы интерфейса приложения, потому что на планшете/кофе-машине системные кнопки Android будут недоступны;
- рекомендации после оплаты должны быть выбираемыми и закрываемыми.

Отдельно этот контракт фиксирует, как использовать новые материалы:

- `net.payinpayout.tso-master.tar.gz` — как справочник по старому терминальному приложению, его конфигурациям, экранам, устройствам, оплатам, лояльности и фискальным сценариям;
- `API web-фискальник.docx` — как справочник для будущего слоя фискализации;
- `Команды смесителя (5).doc` — как справочник для будущего слоя смесителя/лимонадной/чайной станции;
- `Техническое_задание_на_Андройд_приложения.docx` — как внешний источник границ проекта.

В v0.3 эти материалы **не превращаются в боевые интеграции автоматически**. Они добавляются в проект как источники и учитываются в архитектуре. Реальную интеграцию с POS, фискальником, Raspberry Hub, смесителем, чайной и лимонадной станциями нужно делать отдельными контрактами.

## 3. Классификация задачи по контрактной методологии

### 3.1. Тип A — уже есть в контракте/ожидаемом поведении, но работает неправильно

К этому типу относятся:

1. переключатель «У меня свой стакан»;
2. корректное добавление сиропа как настройки товара;
3. закрытие окна добавления купона;
4. выбор правильного напитка из каталога;
5. удаление товара/заказа без перехода в устаревший экран;
6. кнопка «назад» внутри экрана «Ваш заказ»;
7. кнопка «назад» внутри лояльности;
8. закрытие всплывающего окна рекомендации;
9. выбор разных рекомендованных предложений.

Причина: эти действия уже ожидаются пользователем из текущего интерфейса и схемы экранов. Если элемент нарисован и выглядит активным, он должен работать.

### 3.2. Тип B — новая или уточнённая функциональность

К этому типу относятся:

1. экранная клавиатура для купона;
2. экранная клавиатура для лояльности;
3. явное отображение добавленного сиропа и возможность удалить именно этот сироп;
4. динамическое отображение выбранного напитка поверх статического PNG;
5. динамическое отображение актуальной корзины поверх статического PNG;
6. добавление новых справочных документов в проект;
7. первичный разбор архива `net.payinpayout.tso-master.tar.gz` и создание заметок по нему в документации проекта.

Причина: в v0.2.2 большая часть экранов — это статические PNG с горячими областями. Для исправления ошибок нужна небольшая динамическая прослойка состояния и отображения.

## 4. Общий принцип реализации v0.3

v0.3 не должна становиться большой переработкой архитектуры. Нужен хирургический шаг:

- сохранить текущий Kotlin-проект;
- сохранить текущий способ отображения PNG-экранов;
- сохранить текущую сборку из Windows CLI;
- не подключать AndroidX, Compose, Flutter и тяжёлые библиотеки без отдельного согласования;
- добавить только то, что нужно для исправления текущих ошибок;
- не внедрять реальные POS/API/фискальные/устройственные интеграции в этом шаге.

При этом нужно признать слабое место текущего MVP: если экран целиком является картинкой, то выбранный товар, сироп, стакан, купон и состав корзины не могут честно отображаться без динамических надписей и/или небольших нативных элементов поверх PNG.

Поэтому для v0.3 разрешается добавить поверх PNG:

- динамические текстовые подписи;
- динамические области состояния;
- простую экранную клавиатуру;
- простые кнопки закрытия/удаления/назад;
- небольшое всплывающее окно рекомендации;
- актуальные строки корзины.

## 5. Целевое поведение по найденным ошибкам

### 5.1. [Добавление товара] Переключатель «У меня свой стакан»

**Текущее состояние:** переключатель не меняет состояние.

**Целевое поведение:**

- при открытии `ITEM_ADD` у выбранного товара есть состояние `ownCup = false`;
- нажатие на область «У меня свой стакан» переключает состояние `false → true → false`;
- состояние должно быть визуально видно пользователю;
- при добавлении товара в корзину выбранное состояние сохраняется в строке корзины;
- если товар редактируется, экран должен показывать уже сохранённое состояние.

**Временное правило до уточнения цены:**

- в v0.3 переключатель влияет только на состояние заказа и визуальное отображение;
- скидка, изменение цены, изменение рецепта и команда в кофемашину пока не применяются;
- эти эффекты будут добавлены отдельным контрактом после ответа заказчика.

**Критерий готовности:** пользователь может включить и выключить «У меня свой стакан», добавить товар, вернуться к редактированию и увидеть сохранённое состояние.

---

### 5.2. [Добавление товара] Сироп: добавить, показать, удалить

**Текущее состояние:** нажатие «Добавить сироп» показывает только сообщение, но состояние товара не меняется.

**Целевое поведение:**

- при нажатии «Добавить сироп» в текущий товар добавляется сироп;
- после добавления на экране должно быть явно видно, что сироп добавлен;
- должна появиться возможность удалить сироп;
- при удалении сироп исчезает из состояния товара;
- при добавлении товара в корзину сироп сохраняется в строке корзины;
- при повторном редактировании сироп должен отображаться.

**Временное правило до уточнения списка сиропов:**

- в v0.3 используется один мок-сироп по умолчанию, например «Ванильный сироп»;
- если в макете есть несколько сиропов, но нет понятного каталога сиропов, все они пока не моделируются;
- цена сиропа пока не меняет итоговую сумму, если нет явного источника цены.

**Критерий готовности:** пользователь нажимает «Добавить сироп», видит добавленный сироп, удаляет его и видит, что он исчез.

---

### 5.3. [Добавление купона] Клавиатура и закрытие окна

**Текущее состояние:** клавиатура не работает, окно невозможно закрыть.

**Целевое поведение:**

- экран `COUPON_ADD` должен иметь работающую экранную клавиатуру;
- вводимые символы должны отображаться в поле купона;
- должна работать кнопка удаления последнего символа;
- должна работать кнопка очистки поля, если такая кнопка есть в макете или добавлена как служебная;
- должна работать кнопка применения купона;
- должна работать кнопка закрытия окна;
- закрытие окна возвращает пользователя к каталогу или корзине без потери уже набранного заказа.

**Временное правило до интеграции с сервером:**

- купон проверяется в мок-режиме;
- любой непустой купон можно считать «принятым»;
- пустой купон не применяется и показывает понятное сообщение.

**Критерий готовности:** пользователь может набрать купон, удалить символ, закрыть окно, снова открыть и не потерять текущий заказ.

---

### 5.4. [Главное меню] Выбор правильного напитка

**Текущее состояние:** при выборе любого напитка визуально выбирается капучино.

**Вероятная причина:** экран добавления товара использует один и тот же PNG-фон, а выбранный товар не отображается динамически.

**Целевое поведение:**

- каждая карточка каталога должна передавать свой `productId`;
- `pendingProduct` должен указывать на выбранный товар;
- экран добавления товара должен показывать название, цену и, по возможности, изображение именно выбранного товара;
- при добавлении в корзину должна добавляться именно выбранная позиция;
- строка корзины должна показывать именно добавленный товар.

**Временное правило для сохранения верности макету:**

- общий PNG `ITEM_ADD` можно оставить как фон;
- поверх него разрешается вывести динамическую подпись с названием/ценой выбранного товара;
- если подходящего изображения товара нет, картинка на PNG может остаться условной, но текст и состояние заказа должны быть правильными.

**Критерий готовности:** если пользователь нажал американо, в добавлении товара и корзине должен быть американо; если латте — латте; если капучино — капучино.

---

### 5.5. [Главное меню] Удаление товара и устаревшие позиции в «Ваш заказ»

**Текущее состояние:** при попытке удалить товар происходит переход в «Ваш заказ», где показаны неактуальные позиции.

**Целевое поведение:**

- корзина должна быть единым источником истины;
- нельзя полагаться на заранее нарисованные позиции в PNG;
- удаление конкретной строки должно удалять именно эту строку из внутреннего состояния корзины;
- удаление всего заказа должно очищать корзину и возвращать пользователя в каталог без заказа;
- экран «Ваш заказ» должен строить актуальное отображение поверх PNG;
- если корзина пуста, экран заказа не должен показывать старые позиции.

**Временное правило:**

- если точная область удаления конкретной строки пока не размечена, в v0.3 нужно сделать минимум два действия:
  - удалить весь заказ;
  - удалить первую/выбранную строку заказа через отдельную служебную область.

**Критерий готовности:** после удаления позиции она исчезает из состояния и не появляется снова при переходе на «Ваш заказ».

---

### 5.6. [Ваш заказ] Внутренняя кнопка «назад»

**Текущее состояние:** невозможно вернуться назад без системных кнопок Android.

**Целевое поведение:**

- на экране «Ваш заказ» должна быть экранная кнопка назад/закрыть;
- она должна возвращать пользователя в каталог с текущей корзиной;
- системная кнопка Android не должна быть обязательной для сценария;
- физическая/системная кнопка Back, если доступна, может дублировать поведение, но не является основным способом навигации.

**Критерий готовности:** на планшете без системной панели пользователь может выйти из «Ваш заказ» только через UI приложения.

---

### 5.7. [Система лояльности] Клавиатура и кнопка «назад»

**Текущее состояние:** клавиатура не работает, кнопка назад не работает.

**Целевое поведение:**

- экран лояльности должен иметь рабочую цифровую клавиатуру для телефона/кода;
- ввод должен отображаться в поле;
- должна работать кнопка удаления последнего символа;
- должна работать кнопка назад/закрыть;
- закрытие лояльности возвращает пользователя туда, откуда он пришёл: каталог или корзина;
- текущий заказ не должен очищаться при входе/выходе из лояльности.

**Временное правило до боевой Loyalty API-интеграции:**

- любой валидный по длине мок-телефон можно считать успешным входом;
- невалидный ввод показывает понятное сообщение;
- бонусы применяются в мок-режиме без реального расчёта скидки, если нет точного контракта расчёта.

**Критерий готовности:** пользователь может открыть лояльность, ввести телефон, удалить символы, вернуться назад и не потерять заказ.

---

### 5.8. [Выдача товара] [Мы рекомендуем] Выбор разных предложений и закрытие всплывающего окна

**Текущее состояние:** выбирается только «Абонемент на кофе», всплывающее окно нельзя скрыть, другие рекомендации не выбираются.

**Целевое поведение:**

- каждая рекомендованная карточка должна иметь отдельную интерактивную область;
- нажатие на разные предложения должно приводить к разным действиям;
- всплывающее окно рекомендации должно иметь кнопку закрытия;
- закрытие всплывающего окна возвращает пользователя к экрану выдачи/завершения без сброса заказа;
- повторное открытие рекомендации не должно зависать и не должно блокировать выдачу товара.

**Временное правило до уточнения коммерческой логики:**

- «Абонемент на кофе» может открывать QR/экран подписки;
- другое предложение может добавляться в новый мок-заказ или открывать информационное окно;
- третье предложение может быть временно помечено как «подробнее»;
- главное — все карточки должны быть нажимаемыми и окно должно закрываться.

**Критерий готовности:** пользователь может нажать минимум на 2–3 разных предложения и закрыть каждое всплывающее окно.

## 6. Корзина и состояние заказа

Для v0.3 нужно усилить модель состояния, не превращая проект в большую архитектурную переделку.

### 6.1. Минимальные сущности состояния

Внутри приложения должны быть представлены:

- выбранный товар;
- текущая строка редактирования;
- корзина;
- настройки строки:
  - количество;
  - свой стакан;
  - сиропы;
  - купон, если применён;
- состояние экранного ввода:
  - ввод купона;
  - ввод телефона/кода лояльности;
- состояние рекомендации:
  - открыта/закрыта;
  - выбранное предложение.

### 6.2. Правило единого источника истины

PNG-экран не является источником истины. Источник истины — состояние приложения.

Если в PNG нарисован капучино, но пользователь выбрал американо, приложение должно явно показывать пользователю, что выбран американо, и в корзину должен попасть американо.

Если в PNG «Ваш заказ» нарисованы старые позиции, приложение должно перекрыть/дополнить экран актуальными строками корзины.

## 7. Навигация

### 7.1. Главный принцип

Все пользовательские сценарии должны быть доступны без системных кнопок Android.

Это особенно важно для Jetinno JL22 и похожих вендинговых точек, где приложение работает в полноэкранном режиме, а системная панель скрыта.

### 7.2. Обязательные экранные действия

В v0.3 должны быть работающие экранные способы:

- закрыть добавление товара;
- закрыть добавление купона;
- закрыть поиск;
- выйти из «Ваш заказ»;
- выйти из лояльности;
- закрыть ввод email/чека;
- закрыть рекомендацию;
- вернуться с выдачи/справки;
- начать новый заказ.

### 7.3. История экранов

Текущую историю экранов можно сохранить, но нельзя полностью полагаться только на неё.

Для ключевых экранов должны быть явные правила возврата:

- из добавления товара → каталог с текущей корзиной;
- из купона → каталог/корзина;
- из заказа → каталог с текущей корзиной;
- из лояльности → экран, откуда пришли;
- из рекомендации → экран, где рекомендация была открыта;
- из оплаты → выбор способа оплаты или заказ;
- из выдачи → завершение оплаты/справка/новый заказ.

### 8.1. Где нужна клавиатура

В v0.3 экранная клавиатура нужна минимум на двух экранах:

- добавление купона;

### 8.2. Требования к клавиатуре

Клавиатура должна:

- работать без системной клавиатуры Android;
- иметь крупные зоны нажатия;
- отображать введённый текст;
- поддерживать удаление последнего символа;
- поддерживать очистку поля, если это не ломает макет;
- не перекрывать критичные кнопки;

### 8.3. Типы ввода

- купон: буквы/цифры, в v0.3 допустимо ограничиться цифрами и латинскими символами, если русская клавиатура не требуется;
- лояльность: телефон, цифры, возможно `+`, но лучше хранить в формате, который позже потребуется Loyalty API.

## 11. Риски и неоднозначности

### 11.1. Риск статических PNG

Текущие экраны выглядят красиво, но они статичны. Если поверх них не добавлять живые элементы, невозможно честно показать выбранный товар, сироп, купон и корзину.

Решение v0.3: добавить минимальный динамический слой поверх PNG.

### 11.2. Риск несовпадения с Figma

Динамические подписи могут немного отличаться от исходного макета.

Решение v0.3: делать подписи аккуратно, поверх зон, где они не ломают восприятие. Точную визуальную полировку вынести на следующий круг обратной связи.

### 11.3. Риск неправильной логики сиропа и стакана

Неясно, меняют ли сироп и свой стакан цену, рецепт, бонусы или команду кофемашине.

Решение v0.3: хранить состояние и показывать его, но не менять цену и рецепты без подтверждения.

### 11.4. Риск рекомендаций

Неясно, что именно должно происходить при выборе каждого рекомендованного предложения.

Решение v0.3: сделать разные карточки активными и закрываемыми; коммерческую логику зафиксировать позже.

### 11.5. Риск старого TSO-архива

Старый архив большой, содержит десктопные, Raspberry Pi, Windows, Java, DLL/JAR и ресурсные части. Бездумное включение в Android-проект может сломать сборку.

Решение v0.3: добавить только справочные заметки; код и бинарные зависимости не переносить.

### 11.6. Риск реальной периферии

Фискальник, смеситель, POS и Raspberry Hub требуют аккуратных отдельных контрактов. Ошибка в этих слоях может привести не просто к UI-багу, а к неправильной оплате, отсутствию чека или некорректной выдаче товара.

Решение v0.3: не смешивать UI bugfix с боевыми интеграциями.
