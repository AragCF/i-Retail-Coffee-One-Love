# S3 — анализ загруженной документации: отдельная фискализация без кассового device

Версия: 0.5.80  
Дата: 22.09.2026  
Статус: DOCUMENTATION_FINDING

## Главный вывод

Загруженный документ `API web-фискальник.docx` описывает отдельный i-Retail API для внешних систем, который:

- создаёт заказ в БД i-Retail для канала «фискализация интернет заказа»;
- не требует `device_id` во входных данных;
- не требует `order_counter`, `operation_counter`, `refund_counter`;
- не требует `shift_id` и `check_counter`;
- авторизуется через отдельные `api_key + login`;
- принимает `external_order_id`, товары, суммы оплаты и данные чека;
- позволяет затем опрашивать статус фискализации;
- поддерживает callback об успешной/неуспешной фискализации;
- в результате успешной фискализации возвращает `device_id` уже фактического фискализатора, fiscal number и URL электронного чека.

То есть найден отдельный путь фискализации, который не зависит от нашего текущего блокера с кассовым устройством для `iretail/order/synchronize`.

## Что это меняет

Ранее S3 фактически смешивал две задачи:

1. синхронизация обычного заказа в Retail API;
2. фискализация и получение электронного чека.

Документы показывают, что эти задачи могут быть независимыми.

### Контур A — Retail order synchronization

`iretail/order/synchronize` по-прежнему требует:
- device;
- counters;
- shift;
- кассовую семантику.

Этот контур остаётся заблокирован без правильного `workplace_cashier` / `self_service_terminal` или официального альтернативного контракта.

### Контур B — Fiscalization

`cloud-fiscal/order/create` документирован как внешний API и не содержит зависимостей от counters/shift.

Следовательно, получение фискального чека потенциально можно реализовать независимо от завершения контура A.

## Важное ограничение

Документ web-фискальника датирован 2019 годом и использует endpoint `kassa.i-bonus.me`.

Более новое техническое задание проекта прямо разделяет:
- Retail API adapter;
- Fiscal adapter;
- POS adapter;
- Device adapter.

Также ТЗ указывает, что онлайн-касса предоставляется отдельным API и провайдер может меняться. В другом ТЗ уже указан «Первый ОФД» как целевой оператор.

Поэтому старый cloud-fiscal API нельзя молча считать текущим боевым контрактом. Его надо либо подтвердить у I-Retail, либо использовать как доказательство архитектурного разделения и реализовать актуальный Fiscal adapter через текущего оператора.

## Что можно снять из старого списка вопросов

Для задачи **фискализации** больше не обязательно выяснять:
- какой `type_slug` у кассового device;
- где брать order/operation/refund counters;
- где брать shift/check_counter;
- как активировать кассовый device.

Эти вопросы остаются только для `order/synchronize`.

## Новые точные вопросы

1. Поддерживается ли сейчас `/api/cloud-fiscal/order/create`?
2. Если да, можно ли для Coffee One Love получить `api_key` канала продаж и login?
3. В какой канал/профиль будут попадать созданные этим методом заказы?
4. Заменяет ли этот API необходимость `iretail/order/synchronize` для нашего unattended-сценария или он предназначен только для фискализации?
5. Если cloud-fiscal API устарел, какой актуальный внешний fiscal API следует использовать?
6. Подтверждается ли переход на Первого ОФД как текущего fiscal provider?

## Архитектурное решение до ответа

Не связывать POS-оплату, Retail order sync и Fiscalization в один адаптер.

Оставить три независимых границы:
- POS adapter — подтверждает факт оплаты;
- Retail adapter — синхронизирует бизнес-заказ;
- Fiscal adapter — формирует фискальный чек.

Это соответствует загруженному ТЗ и уменьшает риск блокировки всего приложения одной серверной зависимостью.
