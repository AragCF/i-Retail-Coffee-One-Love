# v0.5.22 — результат локальной изоляции SmartSkyPOS на Kozen

Контрольный платёж 1,00 RUB был выполнен непосредственно на Kozen P12 через типизированный SmartSkyPOS Binder-клиент. В цепочке не участвовали JL22, USB/AOA, production bridge и основной i-Retail UI.

Результат:

```text
code=0
approved=false
message=Отказано
rc=99
rrn=625701637880
amount=1.00
currency=643
terminalId=12000679
receipt=9
```

Последующее локальное `getLastTransaction()` вернуло тот же receipt=9, RRN, сумму и `rc=99`.

Следовательно, повторяющийся `rc=99` не создаётся JL22, USB/AOA или production bridge. Причина находится ниже нашего транспортного слоя: SmartSkyPOS/терминальная конфигурация Kozen/эквайринговый контур.

Во время операции SmartSkyPOS переходил в состояние `31 / Обмен данными`, затем вернулся в `READY(0)`. Актуальный TerminalData сообщает:

- ПО `1.9.19-RC.1.11057-BETA`;
- прошивка `2.3.70.20250605`;
- профиль/точка доступа `VPP_BETA_TMS_V1`, активна;
- host `185.162.94.67`, port `9221`;
- merchantId `J500523`;
- TID `12000679`;
- операция `Оплата / 00 / payment`;
- валюта `643`.

IP `185.162.94.67` доступен с Kozen по ICMP без потерь в момент проверки. Это подтверждает базовую сетевую связность, но не заменяет проверку TCP:9221 и не доказывает корректность терминальной/merchant-конфигурации на стороне процессинга.

Следующий безопасный шаг — только чтение: история receipt 1..9, свежий TerminalData, системное время/маршрут, TCP-доступность host:9221 и метаданные SmartSkyPOS/com.pos.service. Для этого подготовлен `SMARTSKYPOS_08_READONLY_ACQUIRER_AUDIT.bat` и публикация `GIT_112_PUBLISH_ACQUIRER_AUDIT.bat`.
