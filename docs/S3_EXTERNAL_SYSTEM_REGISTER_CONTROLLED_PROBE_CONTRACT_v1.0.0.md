# S3 — контракт пробной регистрации для внешней системы

**Версия контракта:** 1.0.0
**Дата:** 21.09.2026
**Статус:** PROPOSED_NOT_APPROVED

## Коротко человеческим языком

У устройства I-Retail есть два разных кода:
- обычный `code` — он совпадает с тем, что уже лежит у нас в конфигурации;
- отдельный `external_code` — он другой.

Обычная регистрация `device/register(code)` уже была один раз проверена и сервер её отверг без видимых изменений.

В документации есть другой метод:

`iretail/device/register-external-system(external_code)`

Его описание буквально означает: «зарегистрировать устройство для внешней системы». Это гораздо лучше соответствует нашей задаче интеграции внешнего приложения с I-Retail.

Но это всё равно регистрационный метод, то есть он может изменить состояние сервера. Поэтому нужен отдельный контракт и отдельное разрешение.

## Что уже доказано

- в канале есть device `3476` типа `coffee_machine`;
- его обычный server `code` существует, длина 4 и совпадает с текущим config `device_code`;
- его `external_code` существует, длина 4 и **не совпадает** с обычным code;
- документация связывает `external_code` именно с `device/register-external-system`;
- метод `register-external-system` принимает `external_code`;
- в ответе он документирован как источник `device_id`, `channel_id`, `type_slug`, `device_inner_id` и трёх counters;
- документация по-прежнему описывает `type_slug` как `workplace_cashier` или `self_service_terminal`;
- открытая смена в ответе этого метода не документирована, поэтому смену после вызова можно только перечитать отдельным read-only методом.

## Что предполагается, но ещё не доказано

Главная рабочая гипотеза:

`external_code` кофемашины 3476 предназначен для подключения внешней системы и через `register-external-system` сервер может вернуть отдельную кассовую/self-service сущность для синхронизации заказов.

Это гипотеза, а не факт. Один контролируемый вызов должен её проверить.

## Разрешённый будущий сценарий

После явного одобрения этого контракта пробник может:

1. Авторизоваться.
2. Read-only получить список устройств канала.
3. Read-only получить `device/get-device-info` для 3476.
4. Взять `external_code` **только в память**; не выводить его и не публиковать.
5. До изменяющего вызова создать устойчивую одноразовую marker-метку.
6. Выполнить **ровно один**:
   `iretail/device/register-external-system(external_code)`.
7. Не выполнять автоматический повтор, даже при тайм-ауте.
8. После ответа только read-only перечитать список устройств.
9. Если сервер вернул `device_id`, read-only получить его device-info и `shift/get-current-active-shift`.
10. Сохранить только безопасный отчёт и остановиться.

## Жёсткие ограничения

- `external_code` не попадает в консоль, Git или ZIP;
- один регистрационный вызов максимум;
- curl retry=0;
- никаких redirects у изменяющего вызова;
- никакой автоматической записи returned `device_id` в конфигурацию;
- никакой автоматической связи returned device с coffee_machine 3476;
- `order/synchronize` запрещён;
- платежи запрещены;
- открытие/закрытие смены запрещено;
- `employee/authorize` запрещён;
- команды кофемашине запрещены;
- `device/update-info` запрещён;
- обычный `device/register` повторно запрещён.

## Если результат неопределённый

При тайм-ауте, обрыве сети или неразбираемом ответе:
- результат = `EXTERNAL_REGISTER_RESULT_UNCERTAIN`;
- повтор `register-external-system` запрещён;
- разрешены только read-only проверки состояния;
- дальнейшее решение принимается после анализа отчёта.

## Что будет считаться хорошим результатом

Хороший исследовательский результат — сервер явно отвечает и мы узнаём:
- returned `device_id`;
- returned `type_slug`;
- `channel_id`;
- три counters;
- появился ли новый device в канале;
- какая активная смена у returned device, если она существует.

Даже успешный результат не включает `order/synchronize` автоматически.

## Что нужно от пользователя

Для перехода к реализации изменяющего вызова нужно отдельное явное согласие именно на этот новый метод:

**«Одобряю один пробный register-external-system».**
