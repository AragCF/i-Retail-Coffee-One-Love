# i-Retail: обновление, сборка и отправка отчёта одним запуском

Дата: 26 сентября 2026 года. Версия сценария: 1.0.1. Загрузчик START_IRETAIL.bat: протокол 1, редакция 1.0.0.
Версия приложения остаётся 0.5.128-device-binding: её исходники этим изменением не правятся.

## Запуск

Сохранить `START_IRETAIL.bat` в существующую рабочую папку:

`C:\54\Projects\!0719 - Coffee\Stage 02\Git\i-Retail-Coffee-One-Love`

Запустить двойным щелчком либо из обычного cmd.exe:

```bat
cd /d "C:\54\Projects\!0719 - Coffee\Stage 02\Git\i-Retail-Coffee-One-Love"
START_IRETAIL.bat
```

Предварительно выполнять `git pull`, менять ветку вручную, распаковывать выпуск или запускать MAIN_41 не требуется. Скрипт получает ветку `v0.5.128-device-binding`, извлекает служебный сценарий из конкретного полученного коммита и обновляет рабочую копию только вперёд. Он не выбирает последнюю экспериментальную ветку по номеру и не переключает проект на `main`.

В репозитории исходник запускающего файла хранится как `tools/START_IRETAIL.bat`. Копия в корне предназначена для удобного запуска и не должна коммититься вместе с исходниками. Это один пользовательский запускаемый файл, а не монолит: обновляемая реализация загружается из GitHub автоматически.

Необходимы уже настроенные Git с доступом к репозиторию, Windows PowerShell 5.1, JDK и Gradle/Android SDK, которыми ранее собирался проект. Скрипт не устанавливает системное ПО и не запрашивает секреты Retail на компьютере. Если Git потребует вход, используется его штатный механизм; открытый токен в адрес origin не добавлять. Не менее 2 ГБ свободного места проверяется перед сборкой. Поиск Android SDK и сборку выполняет существующий `BUILD_WINDOWS_CLI.bat`.

## Что выполняется

1. Проверка адреса origin и получение утверждённой ветки из GitHub.
2. Проверка локальных изменений и обновление рабочей копии без принудительного сброса.
3. Местная сборка проверочного приложения с имеющимся ключом подписи.
4. Выбор JL22 по точному совпадению product/model/device и установка APK через `adb install -r`.
5. Открытие приложения в standalone-режиме с выключенной реальной оплатой. Наблюдение за процессом, связью ADB, состояниями привязки/каталога/канала и распознанными аварийными событиями.
6. По нажатию Enter — создание одного ZIP только с подготовленными полями диагностики и контрольными суммами.
7. Отправка этого ZIP отдельным коммитом в диагностическую ветку и проверка хеша на удалённой стороне.

При обнаружении одной JL22 для выбора достаточно Enter. Если интерфейсов несколько, указать нужный номер. Если машина пока не подключена, можно подключить USB и повторить поиск или ввести известный адрес IPv4:порт для `adb connect`. Чужие устройства, включая Kozen, не допускаются к установке этого приложения.

Во время наблюдения работать с экраном JL22. Enter в окне компьютера завершает сбор; через 30 минут сбор также заканчивается. Краткое обновление состояния выполняется примерно каждые три секунды после завершения предыдущего опроса. При обрыве ADB запрос ограничен тайм-аутом, никакой самовольной смены устройства или перезапуска приложения нет. При нормальной связи Enter обрабатывается после текущего опроса, не обязательно мгновенно.

## Первоначальная привязка

Перед живой активацией перевыпустить прежний PIN в личном кабинете. Ввести новый PIN и реквизиты только на экране JL22. Скрипт не предъявляет PIN, не нажимает «Привязать» и не выполняет серверных запросов регистрации сам.

При неизвестном результате активации не повторять PIN и не удалять данные. При сохранённой привязке и ошибке получения каталога повторять только загрузку настроек. Присутствие приложения в процессах не является доказательством успешной привязки.

## Результаты и публикация

Локальные результаты: `one_click_logs\<дата_время_идентификатор>\`.
Краткий последний итог: `one_click_logs\LAST_RESULT.txt`.
Диагностическая ветка: `diag-oneclick-<дата_время_идентификатор>`.
Файл внутри Git: `test_reports/one-click/IRETAIL_<дата_время_идентификатор>.zip`.

`GIT_REPORT_SENT` означает, что отправка закончилась и удалённая ссылка указывает на ожидаемый коммит. Это не означает успешной привязки: её наблюдённое состояние указано отдельно в RESULT.

`GIT_REPORT_PENDING` означает, что ZIP и подготовленный коммит остались локально. Следующий успешный запуск загрузчика повторяет отправку подготовленных отчётов, а затем выполняет обычный цикл. Вне работающего скрипта фонового планировщика нет. Если ошибка произошла до подготовки коммита/квитанции, автоматическая повторная отправка такого архива не заявляется: он остаётся локально для отдельного разбора.

Отчёт публикуется через отдельный временный индекс Git. Рабочая ветка и подготовленные пользователем изменения не используются как содержимое диагностического коммита. Ветка отчёта опирается на полученный серверный исходный коммит, а не на произвольные местные коммиты. Принудительной отправки нет.

ZIP содержит ровно пять файлов: `report.json`, `events.json`, `build-summary.json`, `README.md`, `SHA256SUMS.txt`. В нём есть версия сценария и приложения, хеш исходников/APK, этап и результат выполнения, состояния процесса/связи, разрешённые состояния привязки, числовые счётчики каталога/служб и распознанные места аварии в коде. Неизвестные строки не переносятся в отчёт.

Полные журналы локальных команд сборки и Git остаются в подкаталоге `local`. Не отправлять весь `one_click_logs`: там могут находиться местные технические подробности. В Git идут только перечисленные подготовленные сведения. Не выгружаются APK, личный реестр доступов, настройки учётной записи, снимки экрана, PIN, пароли, токены, исходные сообщения API и полный logcat. Сырой logcat этим сценарием вообще не сохраняется на диск.

Отдельная `delivery.json` фиксирует доставку. Сам ZIP создаётся до отправки, поэтому не может содержать доказательство собственной последующей доставки; итог отправки смотреть в квитанции или LAST_RESULT.txt. Отсутствие события в выборке не доказывает, что его не было: кольцевой буфер Android и выбранный предел чтения могут потерять очень старые либо слишком частые записи.

## Безопасные остановки

Локальные изменённые или подготовленные к коммиту файлы не стираются и не прячутся. Если они мешают обновлению, сценарий останавливается с `LOCAL_CHANGES_PRESERVED`. Неучтённые файлы в каталогах исходников также блокируют сборку. Своих коммитов в целевой ветке скрипт не отбрасывает и не сливает автоматически.

При несовпадении подписей установка прекращается: приложение удалять нельзя. Нужен прежний ключ местной сборки. При недостатке диска запуск сборки блокируется. Сам объединяющий сценарий не вызывает clean и не очищает кэш; прежний BUILD_WINDOWS_CLI сохраняет собственную ранее введённую политику для низкого свободного места, поэтому запас диска следует оставлять и во время сборки.

Нельзя запускать скрипт одновременно с изменением исходников другой программой. Для двух копий самого скрипта предусмотрена блокировка. Перед установкой проверяется неизменность исходников/коммита; при обнаруженном занятом состоянии привязки установка не начинается. Это не универсальное доказательство отсутствия любой финансовой операции в прежних версиях: обновлять следует во время обслуживания, а не во время оплаты покупателем.

При ошибке прислать `LAST_RESULT.txt` или точный завершающий код. Для успешного прогона достаточно сообщить `GIT_REPORT_SENT` и имя ветки: сами результаты уже в GitHub.
