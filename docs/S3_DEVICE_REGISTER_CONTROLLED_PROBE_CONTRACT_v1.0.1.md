# S3 — контракт контролируемого device/register

**Версия контракта:** 1.0.1  
**Дата:** 21.09.2026  
**Статус:** APPROVED_FOR_SINGLE_PROBE  
**Исполняющий выпуск:** v0.5.64-s3-device-register-probe.

## 1. Цель

Получить актуальные серверные значения, которые опубликованная документация I-Retail выдаёт через:

`POST /api/iretail/device/register`

Документированный вход:
- `device_code`.

Документированный ответ:
- `device_id`;
- `channel_id`;
- `type_slug`;
- `device_inner_id`;
- `counters.order_counter`;
- `counters.operation_counter`;
- `counters.refund_counter`;
- `counters.date`;
- `shift.id`;
- `shift.check_counter`.

Документация дополнительно ограничивает описанный `type_slug` значениями:
- `workplace_cashier`;
- `self_service_terminal`.

Это **не совпадает** с типом найденной серверной записи `device_id=3476`, которая имеет тип `coffee_machine`.

Следовательно:
- будущий результат `device/register` нельзя автоматически отождествлять с кофемашиной 3476;
- пробник не должен переписывать локальную конфигурацию `device_id`;
- возвращённый `type_slug` используется только как наблюдение;
- если сервер создаёт/возвращает отдельное кассовое или self-service устройство, пробник фиксирует это и останавливается после read-only проверки «после»;
- никакая связь «self_service_terminal = coffee_machine 3476» не допускается без отдельного доказательства.
Цель пробника — **исследовать фактическую семантику одного штатного вызова**, а не начать рабочую регистрацию или синхронизацию заказов.

## 2. Почему требуется отдельное согласование

Аудит всей опубликованной документации нашёл 28 страниц контроллеров I-Retail и 18 упоминаний счётчиков.

Документированные методы чтения смены дают только `check_counter`.

Полный набор `order_counter / operation_counter / refund_counter` документирован только рядом с методами, которые по назначению изменяют или синхронизируют состояние:

- `device/register`;
- `device/register-external-system`;
- `order/synchronize`.

`device/update-info` после точного разбора исключён как источник counters: он принимает сведения об устройстве/ОС/периферии и возвращает только признак успешного обновления.

Поэтому безопасной документированной read-only альтернативы `device/register` не найдено.

## 3. Известное состояние до пробника

На 21.09.2026 предыдущие read-only проверки подтвердили:

- `channel_id=5676`;
- `profile_id=2512`;
- `currency_id=643`;
- configured `device_id=6287` не определяется сервером как касса;
- единственное найденное устройство канала: `device_id=3476`, тип `coffee_machine`;
- устройство 3476 было offline, последний известный ping — 29.05.2026;
- для 3476 возвращалась смена `164570`, открытая 29.05.2026;
- эту смену нельзя считать актуальной для нового заказа;
- DRY_RUN v2 принят живым испытанием и намеренно оставляет device/shift/counters незаполненными.

Эти сведения являются снимком, а не гарантией текущего состояния на момент будущего пробника.

## 4. Разрешённый будущий сценарий

После явного одобрения контракта пробник может выполнить следующую последовательность.

### Шаг A — read-only состояние «до»

1. Авторизация.
2. `iretail/channel/get(channel_id)`.
3. `iretail/device/get-by-channel-id(channel_id)`.
4. Для найденных устройств — только:
   - `iretail/device/get-device-info(device_id)`;
   - `iretail/shift/get-current-active-shift(device_id)`.
5. Сохранение безопасного снимка «до».

### Шаг B — единственный изменяющий вызов

Ровно **один** вызов:

`iretail/device/register(device_code)`

Условия:
- значение `device_code` берётся из существующей локальной конфигурации;
- значение не выводится в консоль и не попадает в отчёт;
- автоматические повторные попытки запрещены;
- цикл, повтор, запасной register-route или register-external-system запрещены;
- ответ `type_slug` не выбирает и не заменяет устройство автоматически;
- ни `device_id`, ни `type_slug` из ответа не записываются в рабочую конфигурацию.

### Шаг C — состояние «после»

Если сервер вернул определённый ответ, выполняются только read-only проверки:

1. повторный `device/get-by-channel-id(channel_id)`;
2. `device/get-device-info` для возвращённого/обнаруженного device_id;
3. `shift/get-current-active-shift` для возвращённого device_id;
4. сравнение состояния «до/после».

## 5. Неопределённый результат

Если единственный `device/register` завершился:

- сетевым тайм-аутом;
- обрывом соединения;
- отсутствием разбираемого ответа;
- состоянием, при котором неизвестно, принял ли сервер запрос,

то результат обозначается как **REGISTER_RESULT_UNCERTAIN**.

После этого:

- повторный `device/register` запрещён;
- допускаются только read-only проверки состояния;
- пробник завершается;
- решение принимается человеком после анализа отчёта.

## 6. Жёстко запрещено

Пробник не должен вызывать:

- `device/register-external-system`;
- `device/update-info`;
- `shift/get-current` — документация допускает создание смены при её отсутствии;
- `shift/open-shift`;
- `shift/close-shift`;
- `employee/authorize`;
- `payment-in/create`;
- `order/synchronize`;
- любые методы приготовления или оборудования;
- автоматический повтор финансовой или регистрационной операции.

## 7. Что не считается разрешением

Не являются разрешением:

- существование `device_code` в конфигурации;
- факт, что приложение уже авторизуется в I-Retail;
- предыдущая общая договорённость «продолжать без подтверждения»;
- наличие метода в официальной документации;
- создание этого контрактного файла.

Для реализации и последующего запуска изменяющего вызова требуется явное одобрение именно этого контракта.

## 8. Что будет считаться успехом исследования

Успех пробника не равен успеху будущей интеграции заказа.

Исследовательский успех означает, что после одного вызова доказательно установлены:

- фактически возвращённый `device_id`;
- фактически возвращённый `type_slug`;
- является ли возвращённое устройство новой/отдельной записью относительно `coffee_machine 3476`;
- `channel_id`;
- все три counters и их date;
- shift id/check_counter, если сервер их возвращает;
- различия состояния канала/устройства/смены до и после;
- отсутствие неожиданных дополнительных изменений, насколько их можно увидеть доступными read-only методами.

Даже при успехе `order/synchronize` остаётся запрещён до отдельного анализа результата и следующего контрактного решения.

## 9. Возможные последствия

До живого опыта нельзя доказать, что `device/register` идемпотентен.

Потенциально он может:
- зарегистрировать отдельное устройство типа `workplace_cashier` или `self_service_terminal`, а не кофемашину;
- обновить серверную регистрацию существующего устройства;
- создать или привязать запись устройства;
- обновить состояние/метаданные/время активности;
- повлиять на серверно хранимые counters или связанную смену.

Поэтому автоматический откат не предусматривается: неизвестную серверную мутацию нельзя надёжно «отменять» догадкой.

## 10. Условие перехода

Текущий статус:

**APPROVED_FOR_SINGLE_PROBE**

Пользователь явно одобрил одноразовый пробный `device/register` 21.09.2026 после объяснения простыми словами: снять состояние «до», один раз вызвать штатную регистрацию устройства, снять состояние «после» и затем отдельно разобрать результат.

Одобрение распространяется только на сценарий этого контракта:
- один `device/register(device_code)`;
- без автоматического повтора;
- без изменения локального `device_id`;
- без `order/synchronize`, платежей, открытия/закрытия смены и команд оборудования;
- после опыта дальнейшее решение снова принимается по результатам отчёта.

Добавленные после первоначального объяснения ограничения по `type_slug` только сужают автоматическое поведение и не расширяют объём разрешения.
