# PROTOCOL_iRetail_Android_UI_v0.2

Статус: **кандидат на утверждение; рамка первого этапа согласована устно в чате**  
Проект: **i-Retail / Android-фронт для робо-кофейни Jetinno JL22**  
Платформа: **Android 6+**  
Основной стек реализации после утверждения: **Kotlin + нативный Android UI**  
Код приложения по этому документу не пишется до отдельного подтверждения перехода к реализации.

Версия v0.2 фиксирует решение: **первый выпуск делается как UI MVP на Kotlin с мок-данными, экранными переходами и явными заглушками для спорных интеграций**.

---

## 1. Назначение документа

Этот документ фиксирует контракт поведения Android-интерфейса i-Retail на основе переданной схемы экранов и архива с PNG-макетами.

Контракт нужен, чтобы перед программированием согласовать:

- какие экраны есть в приложении;
- как пользователь переходит между экранами;
- какие состояния заказа существуют;
- где заканчивается ответственность фронта;
- какие события фронт должен получать от серверной части, платёжного слоя и исполнительного слоя кофемашины;
- какие решения можно временно отложить без блокировки первого UI MVP;
- какие места должны быть закрыты заглушками или отключены настройкой до появления боевых контрактов.

Документ не является исходным кодом и не описывает внутреннюю реализацию классов, Activity, Fragment, ViewModel или сетевых методов.

## 3. Границы текущего контракта

### 3.1. Что входит в общий экранный контракт

В этот контракт входит пользовательский Android-интерфейс:

- заставка;
- каталог напитков;
- добавление и редактирование товара;
- поиск;
- добавление купона;
- добавление еды;
- сценарии микромаркета;
- система лояльности;
- выбор способа оплаты;
- оплата картой через POS;
- онлайн-оплата по QR;
- оплата наличными;
- завершение оплаты;
- отправка чека на email;
- запрос установки стаканчика;
- выдача товара;
- рекламные и сервисные QR-экраны;
- страница ошибки;
- справочная информация для пользователей.

### 3.2. Что входит в первый программный этап v0.2 / UI MVP

Первый программный этап можно начинать без окончательных ответов по спорным интеграциям, если строго соблюдаются правила ниже.

В первый этап входит:

- Android-приложение на Kotlin под Android 6+;
- полноэкранный портретный интерфейс под базовый размер макетов 1080 × 1920 px;
- восстановление структуры экранов по PNG-схеме;
- реализация навигации между экранами согласно этому контракту;
- локальная модель пользовательской сессии;
- локальная модель черновика заказа;
- отображение каталога на мок-данных или локальном JSON;
- добавление, редактирование и удаление товаров в заказе;
- поиск по мок-каталогу;
- экранный сценарий купона без боевой проверки на сервере;
- экранный сценарий лояльности без боевого начисления/списания бонусов;
- экранные сценарии POS, онлайн-оплаты и наличных без реального списания средств;
- экранные сценарии приготовления, выдачи, стаканчика и разогрева без реального запуска оборудования;
- явная маркировка всех мок-режимов и заглушек внутри кода/настроек проекта;
- безопасное поведение: UI не должен создавать впечатление реальной успешной оплаты или выдачи там, где работает заглушка.

### 3.3. Что не входит в первый программный этап v0.2

В первый программный этап не входит боевая реализация:

- серверных REST/WebSocket API;
- протокола управления кофемашиной JL22;
- протокола POS-терминала;
- протокола купюроприёмника/MDB;
- онлайн-оплаты и подтверждения списания средств;
- фискализации и онлайн-кассы;
- физического API разогрева еды;
- реальной программы лояльности;
- возвратов денег и компенсаций;
- админской панели;
- финальной сборки, подписи APK и развёртывания как промышленного выпуска.

Эти части должны быть описаны в отдельных контрактах или добавлены в этот документ отдельными утверждёнными разделами.

### 3.4. Правило отложенных решений

Отложенные решения не блокируют UI MVP, но должны быть явно отделены от боевой логики.

Разрешено:

- показывать экраны спорного сценария;
- делать переходы между ними;
- использовать мок-данные;
- включать/выключать сценарий настройкой;
- возвращать пользователя в безопасное состояние, если боевой слой не подключён.

Запрещено:

- хардкодить будущий протокол оплаты, MDB, лояльности, JL22 или разогрева еды;
- считать мок-оплату реальной оплатой;
- отправлять команду приготовления без подтверждённого боевого события оплаты;
- скрыто смешивать интерфейсную демонстрацию и реальную работу оборудования;
- делать необратимые действия в железе или платёжном слое без отдельного утверждённого контракта.

### 3.5. Режимы работы первого этапа

В первом этапе должны быть предусмотрены следующие режимы на уровне конфигурации приложения:

| Режим | Назначение | Ограничение |
|---|---|---|
| `UI_DEMO` | Демонстрация экранов и переходов на мок-данных | Не выполняет оплату и команды оборудования |
| `UI_MOCK_ORDER` | Проверка каталога, корзины, поиска и заказа | Заказ существует только внутри приложения |
| `PAYMENT_MOCK` | Проверка экранов оплаты без реального списания | Нельзя считать оплату боевой |
| `MACHINE_MOCK` | Проверка экранов стаканчика, приготовления и выдачи | Нельзя отправлять команды JL22 |
| `INTEGRATION_READY` | Будущий режим для подключения боевых API | Включается только после утверждения отдельных контрактов |

## 5. Главные сущности интерфейса

### 5.1. Товар

Товар — единица каталога, которую пользователь может добавить в заказ.

Виды товаров по макетам:

- кофе / напиток;
- еда;
- товар микромаркета;
- товар, требующий разогрева;
- рекламный или бонусный продукт, связанный с лояльностью.

### 5.2. Заказ

Заказ — набор товаров, выбранных пользователем до момента оплаты.

Заказ должен поддерживать:

- добавление товара;
- удаление товара;
- изменение количества;
- применение купона;
- отображение итоговой суммы;
- переход к выбору оплаты;
- очистку при начале нового заказа;
- восстановление корректного состояния после неуспешной оплаты или ошибки.

### 5.3. Сессия пользователя

Сессия пользователя — временное состояние взаимодействия клиента с терминалом.

Сессия начинается:

- при касании заставки;
- при сканировании товара в микромаркете;
- при выборе товара;
- при переходе из рекламного экрана в каталог.

Сессия завершается:

- после успешного завершения сценария;
- после явной команды «Новый заказ»;
- по таймауту бездействия;
- при критической ошибке;
- при переходе в заставку.

### 5.4. Лояльность

Лояльность — отдельный пользовательский сценарий, который может быть вызван:

- из каталога;
- перед оплатой;
- после завершения оплаты;
- из экрана выдачи товара;
- через рекламный QR-экран.

### 5.5. Исполнительный слой

Исполнительный слой — внешняя для UI часть системы, которая отвечает за:

- приготовление кофе;
- выдачу товаров;
- проверку/ожидание стаканчика;
- разогрев еды;
- получение статусов оборудования;
- отправку событий прогресса.

Фронт не должен самостоятельно принимать решение о физическом приготовлении или выдаче. Он только отправляет согласованные команды и отображает подтверждённые статусы.

## 8. Основные пользовательские сценарии

### 8.1. Сценарий покупки кофе

1. Система находится в `IDLE` и показывает `SCREEN_SAVER_COFFEE` или рекламный экран.
2. Пользователь нажимает кнопку выбора кофе.
3. Система открывает `CATALOG_DEFAULT`.
4. Пользователь выбирает товар.
5. Система открывает `ITEM_ADD`.
6. Пользователь подтверждает добавление.
7. Товар появляется в заказе, сумма пересчитывается.
8. Пользователь может:
   - добавить ещё товары;
   - применить купон;
   - войти в лояльность;
   - перейти к оплате.
9. При переходе к оплате открывается `PAYMENT_METHOD_ALL` или `PAYMENT_METHOD_NO_CASH`.
10. Пользователь выбирает способ оплаты.
11. После успешной оплаты открывается `PAYMENT_COMPLETED`.
12. Если в заказе есть кофе и требуется стаканчик, система показывает `CUP_REQUIRED`.
13. После подтверждения стаканчика начинается `DISPENSE`.
14. Система показывает экран выдачи с нужным количеством прогресс-баров.
15. После завершения пользователь может:
   - начать новый заказ;
   - отправить чек;
   - получить карту лояльности;
   - перейти к рекламному QR-предложению.

### 8.2. Сценарий поиска товара

1. Из каталога пользователь открывает поиск.
2. Открывается `SEARCH_EMPTY_INPUT`.
3. Пользователь вводит запрос.
4. При наличии совпадений система показывает соответствующий экран результатов:
   - `SEARCH_COCO`;
   - `SEARCH_AMER`;
   - `SEARCH_RESULT`.
5. При отсутствии совпадений открывается `SEARCH_NOTHING`.
6. Из результатов можно выбрать товар, добавить его в заказ и перейти к оплате.
7. Из поиска можно вернуться в каталог.

### 8.3. Сценарий купона

1. Пользователь в каталоге или заказе нажимает добавление купона.
2. Открывается `COUPON_ADD`.
3. Пользователь вводит купон.
4. Система отправляет купон на проверку во внешний слой.
5. При успехе:
   - купон применяется к заказу;
   - сумма пересчитывается;
   - пользователь возвращается в каталог или заказ.
6. При ошибке:
   - экран остаётся открытым;
   - показывается понятное сообщение;
   - сумма заказа не меняется.

### 8.4. Сценарий добавления еды

1. Из каталога пользователь выбирает добавление еды.
2. Система открывает `FOOD_SCAN` или сценарий микромаркета.
3. Пользователь сканирует/выбирает товар.
4. Если товар требует разогрева, запускается `HEAT_FOOD_FLOW`:
   - `HEAT_FOOD_1`;
   - `HEAT_FOOD_2`;
   - `HEAT_FOOD_3`;
   - `HEAT_FOOD_DONE`.
5. После завершения товар возвращается в заказ.
6. Далее пользователь может продолжить выбор или перейти к оплате.

### 8.5. Сценарий оплаты картой

1. Из заказа пользователь открывает выбор оплаты.
2. Открывается `PAYMENT_METHOD_ALL` или `PAYMENT_METHOD_NO_CASH`.
3. Пользователь выбирает оплату картой.
4. Открывается `PAYMENT_POS`.
5. Фронт ожидает событие от платёжного слоя.
6. При успешной оплате открывается `PAYMENT_COMPLETED`.
7. При отказе/ошибке оплаты система возвращает пользователя на экран выбора оплаты или показывает ошибку.

### 8.6. Сценарий онлайн-оплаты

1. Из выбора оплаты пользователь выбирает онлайн-оплату.
2. Открывается `PAYMENT_ONLINE_QR`.
3. Пользователь сканирует QR-код.
4. Пока оплата не подтверждена, система показывает ожидание/подтверждение через `PAYMENT_ONLINE_CONFIRM`.
5. При успешной оплате открывается `PAYMENT_COMPLETED`.
6. При истечении времени или ошибке пользователь возвращается к выбору оплаты или видит ошибку.

### 8.7. Сценарий оплаты наличными

1. Из выбора оплаты пользователь выбирает наличные.
2. Открывается `PAYMENT_CASH`.
3. Система показывает внесённую сумму и остаток к оплате.
4. После внесения достаточной суммы пользователь подтверждает оплату.
5. При успехе открывается `PAYMENT_COMPLETED`.
6. Если купюроприёмник недоступен, способ оплаты наличными не должен отображаться или должен быть явно отключён.

### 8.8. Сценарий завершения оплаты и выдачи

1. После успешной оплаты открывается `PAYMENT_COMPLETED`.
2. Если заказ содержит кофе и требуется физический стаканчик, открывается `CUP_REQUIRED`.
3. После подтверждения стаканчика исполнительный слой запускает приготовление.
4. Фронт показывает экран выдачи:
   - один прогресс-бар, если выполняется один тип выдачи;
   - два прогресс-бара, если выполняются две параллельные/последовательные операции;
   - три прогресс-бара, если выполняются три операции.
5. Прогресс должен приходить от исполнительного слоя, а не вычисляться декоративно на фронте.
6. После завершения всех операций заказ считается выданным.

### 8.9. Сценарий отправки чека

1. Из `PAYMENT_COMPLETED` или экрана выдачи пользователь выбирает отправку чека.
2. Открывается `RECEIPT_EMAIL_INPUT`.
3. Пользователь вводит email.
4. Система отправляет email во внешний слой чеков/фискализации.
5. При успехе открывается `RECEIPT_EMAIL_COMPLETE`.
6. При ошибке пользователь остаётся на экране ввода и получает понятное сообщение.

### 8.10. Сценарий лояльности

1. Пользователь открывает лояльность из каталога, заказа, оплаты или после завершения оплаты.
2. Если пользователь не авторизован, открывается `LOYALTY_LOGIN`.
3. После успешной авторизации открывается профиль/бонусный экран:
   - `LOYALTY_PROFILE`;
   - `LOYALTY_PROFILE_FULL`;
   - `LOYALTY_SUBSCRIPTION`.
4. Пользователь может применить бонусы или получить QR-предложение.
5. После применения лояльности сумма заказа пересчитывается.
6. Пользователь возвращается к заказу или оплате.

### 8.11. Сценарии микромаркета

Микромаркет в схеме представлен несколькими режимами. Режим должен задаваться конфигурацией торговой точки.

| Режим | Экранный поток | Предварительная трактовка |
|---|---|---|
| `TRUST_SINGLE` | `TRUST_SINGLE_1` → `TRUST_SINGLE_2` → заказ | Клиент берёт один товар, система доверительно фиксирует выбор |
| `TRUST_MULTI` | `TRUST_MULTI_1` → `TRUST_MULTI_2` → заказ | Клиент берёт несколько товаров |
| `TRUST_MULTI_HEAT` | `TRUST_MULTI_HEAT_1` → `TRUST_MULTI_HEAT_2` → `TRUST_MULTI_HEAT_3` → разогрев/заказ | Несколько товаров, часть может требовать разогрева |
| `TRUST_PLUS` | `TRUST_PLUS_1` → `TRUST_PLUS_2` → `TRUST_PLUS_3` → заказ | Расширенный доверительный сценарий с подтверждением карты/товара |
| `TRUST_PLUS_MULTI` | `TRUST_PLUS_MULTI_1` → `TRUST_PLUS_MULTI_2` → `TRUST_PLUS_MULTI_3` → `TRUST_PLUS_MULTI_ORDER` | Расширенный сценарий на несколько товаров |

Спорный момент: по схеме видно наличие альтернативных сценариев микромаркета, но не хватает текстового описания, чем именно отличаются «Доверие», «Доверие Мульти», «Доверие Плюс» и «Доверие Плюс Мульти» с точки зрения оборудования и бизнес-правил. До реализации эти различия нужно подтвердить.

## 12. Ошибочные состояния

| Ошибка | Как показывать | Что запрещено |
|---|---|---|
| Каталог не загружен | Страница ошибки или сообщение с повтором | Показывать пустой каталог как рабочий |
| Товар недоступен | Сообщение на карточке/в заказе | Давать оплатить недоступный товар |
| Купон не принят | Сообщение в `COUPON_ADD` | Молча менять сумму |
| POS недоступен | Не показывать карту или показать отключённой | Запускать оплату без терминала |
| Онлайн-оплата не создана | Ошибка на экране QR | Показывать старый QR |
| Наличные недоступны | Не показывать наличные или показать отключёнными | Принимать заказ без доступного купюроприёмника |
| Оплата списана, выдача не началась | `ERROR_APOLOGIZE` + поддержка/QR | Молча возвращать в каталог |
| Стаканчик не поставлен | `CUP_REQUIRED` | Начинать кофе без подтверждения, если требуется стакан |
| Выдача сорвалась | `ERROR_APOLOGIZE` или `ERROR_406` | Показывать заказ как успешно выданный |
| Нет связи | Явная ошибка/повтор | Делать вид, что операция успешна |

## 13. Таймауты

Точные значения нужно утвердить отдельно. Пока контракт фиксирует сами типы таймаутов.

| Таймаут | Предлагаемое значение | Поведение |
|---|---:|---|
| Бездействие на заставке | не требуется | Заставка остаётся / меняется по рекламному циклу |
| Бездействие в каталоге без заказа | 60 секунд | Возврат к заставке |
| Бездействие в каталоге с заказом | 90 секунд | Предупреждение, затем сброс заказа |
| Ввод купона | 90 секунд | Закрыть ввод, вернуться к заказу |
| Ввод email | 90 секунд | Закрыть ввод, вернуться к предыдущему экрану |
| Ожидание карты POS | по настройке терминала | Ошибка/возврат к выбору оплаты |
| Ожидание онлайн-оплаты | 120 секунд | Истечение QR, возврат к выбору оплаты |
| Ожидание наличных | 120 секунд | Возврат к выбору оплаты; если внесены деньги — отдельный сценарий |
| Ожидание стаканчика | 60 секунд | Подсказка/поддержка/отмена — требуется уточнить |
| Выдача товара | по данным исполнительного слоя | Ошибка при превышении контрольного времени |

## 14. Правила отображения прогресса выдачи

1. Прогресс должен быть связан с реальными операциями, а не быть только анимацией.
2. Количество прогресс-баров выбирается по составу заказа:
   - один тип операции → один прогресс-бар;
   - два типа операций → два прогресс-бара;
   - три типа операций → три прогресс-бара.
3. Возможные типы операций:
   - приготовление кофе;
   - выдача товара микромаркета;
   - разогрев еды;
   - выдача дополнительного товара.
4. Если внешний слой не умеет отдавать точный процент, фронт может показывать шаговый прогресс только после отдельного согласования.
5. При ошибке хотя бы одного обязательного этапа заказ не считается полностью выполненным.

## 15. Правила полноэкранного режима

Приложение должно работать как интерфейс вендинговой точки.

Требования:

- скрыть системные панели Android, если это допустимо на устройстве;
- запретить случайный выход пользователя из приложения;
- восстанавливаться после перезапуска Activity;
- возвращаться в безопасное состояние после сбоя;
- не терять оплаченный заказ при повороте, перерисовке или перезапуске экрана;
- при критической ошибке показывать понятный экран, а не белый/чёрный экран.

## 18. Definition of Done для первого UI MVP

Первый UI MVP считается готовым, если:

- приложение запускается на Android 6 / API 23;
- приложение открывается в портретном полноэкранном режиме;
- основные экраны соответствуют PNG-макетам в пределах технических ограничений Android 6 и реального экрана JL22;
- все утверждённые переходы работают;

- пользователь не может оплатить пустой заказ даже в мок-режиме;
- пользователь не может запустить реальную выдачу без реального подтверждения оплаты;

- ошибки платежа и выдачи отображаются явно;
- есть безопасный возврат к заставке;
- спорные сценарии либо работают как мок-потоки, либо отключаются настройкой;
- в приложении не захардкожены будущие реальные протоколы POS, MDB, JL22, фискализации, лояльности и разогрева.

Первый UI MVP не считается промышленным выпуском для эксплуатации с реальными деньгами и реальной выдачей товаров.
