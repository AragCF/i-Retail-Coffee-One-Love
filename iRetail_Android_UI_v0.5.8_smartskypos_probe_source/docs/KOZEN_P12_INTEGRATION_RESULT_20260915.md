# Coffee One Love — итог интеграции Kozen P12

Дата фиксации: 15.09.2026  
Проект: i-Retail / Coffee One Love  
Статус: **транспорт, Android-интеграция, SmartSkyPOS Binder-контракт, основной i-Retail UI и восстановление транзакций реализованы и подтверждены на реальном оборудовании. Финальный банковский приёмочный тест ожидает отдельного тестового эквайрингового контура для Kozen.**

---

## 1. Назначение документа

Этот документ фиксирует фактический результат работ по Kozen P12 Mini и служит точкой завершения текущего этапа Kozen перед переключением команды на Vendotek.

Документ описывает не первоначальные предположения, а то, что было проверено на реальном комплекте:

- кофе-машина Jetinno JL22 под Android 6;
- отдельный платёжный терминал Kozen P12 Mini под Android 11;
- физическое USB-соединение между JL22 и Kozen;
- Android Open Accessory (AOA) как рабочий транспорт между двумя устройствами;
- локальный SmartSkyPOS Binder/AIDL-интерфейс на Kozen;
- приложение-мост `i-Retail Kozen Payment Bridge` на Kozen;
- основной интерфейс `i-Retail UI` на JL22;
- инициирование оплаты из основного i-Retail UI;
- защита от повторного финансового вызова;
- восстановление результата операции по истории SmartSkyPOS;
- эксплуатационные режимы «отдельно стоящая кофе-машина» и «кофе-машина в составе киоска».

Узбекский платёжный контур Multicard в этот документ намеренно не включён: его интеграция отложена.

## 2. Итоговая архитектура Kozen

Фактически подтверждённая цепочка имеет вид:

```text
Покупатель
   |
   v
Основной i-Retail UI на JL22 (Android 6)
   |
   |  Payment Coordinator / KozenAoaPaymentClient
   v
USB Host JL22
   |
   |  Android Open Accessory (AOA), bulk endpoints
   v
Kozen P12 Mini (Android 11)
   |
   |  i-Retail Kozen Payment Bridge
   v
SmartSkyPOS local Binder/AIDL service
   |
   v
Платёжный контур / эквайринг
```

Критически важное решение: **полный i-Retail UI не устанавливается на Kozen в промышленной схеме**. На Kozen работает только небольшой bridge-компонент. Пользовательский интерфейс заказа и оплаты остаётся на кофе-машине JL22.

Прямой Android Binder/AIDL не может проходить через USB между двумя Android-устройствами, поэтому Binder используется только локально на Kozen, а между JL22 и Kozen работает собственный безопасный текстовый протокол поверх AOA.

## 3. Физическое USB-соединение и роль устройств

JL22 работает USB Host, Kozen — USB Device/UFP.

До переключения в AOA Kozen реально определялся со стороны JL22 как USB-устройство:

```text
VID:PID = 0e8d:201c
manufacturer = Kozen
product = P12
```

После запуска Android Open Accessory устройство переходит в стандартный Google AOA VID/PID:

```text
18d1:2d01
```

На Kozen при этом фиксировалось:

```text
sys.usb.config=accessory,adb
sys.usb.state=accessory,adb
current_functions=ACCESSORY
```

AOA metadata:

```text
manufacturer=Coffee One Love
model=iRetail Kozen Payment Bridge
```

Это доказало, что физическая линия JL22 → USB → Kozen пригодна не только для обнаружения устройства, но и для двунаправленного прикладного обмена.

## 4. Подтверждение AOA-канала

Первый полноценный тест AOA показал следующий маршрут:

```text
JL22: PING 1001
Kozen Bridge: RX PING 1001
Kozen Bridge: TX PONG 1001 ...
```

Первоначально на JL22 наблюдался timeout, потому что bridge на Kozen был открыт позднее, а PING оставался в очереди. После открытия accessory Kozen прочитал уже переданный PING и вернул PONG. Тем самым было доказано, что транспорт работал, а проблема была только в поведении диагностического клиента.

После увеличения времени ожидания и исправления запуска были подтверждены стабильно:

```text
PING -> PONG
INFO -> INFO
```

И затем более сложные команды поверх того же AOA-канала.

## 5. SmartSkyPOS на реальном Kozen

На Kozen установлен SmartSkyPOS:

```text
package = com.skytech.smartskypos
service = com.crestwavetech.smartskyposservice.SmartSkyPosService
action = com.skytech.smartskypos.ISmartSkyPos
Binder descriptor = com.skytech.smartskyposlib.ISmartSkyPos
```

Версия:

```text
SmartSkyPOS: 1.9.19-RC.1.11057
Terminal software: 1.9.19-RC.1.11057-BETA
Firmware: 2.3.70.20250605
```

Текущая терминальная конфигурация:

```text
TMS ID / serial = P12240612000679
merchantId = J500523
default TID = 12000679
currency = 643 (RUB)
profile = VPP_BETA_TMS_V1
host = 185.162.94.67
port = 9221
```

Терминал рекламирует следующие операции:

```text
Оплата        type=00  transactionType=payment
Отмена        type=71  transactionType=cancel
Сверка итогов type=95
Отчёт         type=97
Возврат       type=20  transactionType=refund
Оплата СБП    type=42  transactionType=qrPayment
Возврат СБП   type=20  transactionType=qrRefund
```

На текущем этапе в основной i-Retail интегрирована только карточная продажа. СБП, возвраты, отмены и сверка не включены в пользовательский сценарий и требуют отдельной приёмки.

## 6. Восстановленный Binder-контракт

По фактическому SmartSkyPOS удалось подтвердить ключевые Binder-транзакции:

```text
1  = getState
4  = getTerminalData
5  = payment
20 = getLastTransaction(TransactionParams)
21 = getTransaction(TransactionParams)
```

Для диагностики и интеграции были восстановлены минимально необходимые Parcelable/AIDL-классы, включая:

- `TransactionParams`;
- `TransactionResult`;
- `TerminalData`;
- `Terminal`;
- `Operation`;
- `Currency`;
- callback-интерфейсы состояния и транзакции.

Важная семантика результата:

> `code=0` означает успешное выполнение вызова SmartSkyPOS API и **не означает**, что банковская операция одобрена.

Финансовый успех в i-Retail разрешается только при достоверном `approved=true` и согласованном банковском `rc` одобрения. `approved=false` всегда считается отказом независимо от `code`.

## 7. Последовательность безопасного запроса оплаты

Перед каждым финансовым вызовом Kozen Bridge выполняет свежую проверку:

1. SmartSkyPOS Binder подключён и жив.
2. `getState()` возвращает `READY(0)`.
3. Свежий `getTerminalData()` возвращает `code=0`.
4. В TerminalData существует карточная операция именно:

```text
type=00
transactionType=payment
currency=643
```

5. Используется TID, фактически объявленный терминалом.
6. Проверяется сумма.
7. Только после этого вызывается `payment()`.

Автоматического повторного `payment()` после исключения, тайм-аута или неоднозначного результата нет.

---

## 8. Идемпотентность и защита от двойного списания

Для каждой попытки основное приложение формирует уникальный `requestId`.

Kozen Bridge хранит состояние запроса в `SharedPreferences` и соблюдает правило:

```text
один requestId -> не более одного вызова SmartSkyPOS.payment()
```

Если такой же `requestId` приходит повторно, bridge возвращает уже известный результат либо статус незавершённой операции и **не выполняет второй финансовый вызов**.

При неопределённом результате используется состояние `UNCERTAIN`. Такое состояние не разрешает автоматический новый платёж.

Для восстановления предусмотрены read-only команды:

```text
GET_PAYMENT_STATUS
GET_LAST_TRANSACTION
GET_TRANSACTION
```

В журналы не записываются PAN, CVV, EMV-данные, имя держателя карты и содержимое чувствительных банковских данных.

Реальная карточная оплата подключена к основному пользовательскому интерфейсу на JL22. Старый демонстрационный механизм, который автоматически считал POS-оплату успешной через фиксированную задержку, для карточного Kozen-сценария больше не используется.

## 10. Подтверждённые финансовые операции

### Ранее успешная контрольная операция

На локальном Kozen SmartSkyPOS была зафиксирована реально одобренная операция 1 RUB:

```text
code=0
approved=true
message=Одобрено
rrn=624801627455
authCode=607605
amount=1.00
currency=643
terminalId=12000679
receipt=2
type=00
```

Эта операция доказала, что аппаратная часть Kozen, считывание карты и SmartSkyPOS в принципе способны проводить банковскую продажу.

### Более поздние отказы

На текущем BETA-контуре несколько операций завершались определённым отказом `rc=99`.

Пример операции из основного i-Retail UI:

```text
amount=57.00
currency=643
terminalId=12000679
receipt=8
rrn=625701637720
approved=false
message=Отказано
rc=99
```

Локальная контрольная операция непосредственно на Kozen, полностью в обход JL22/AOA/production bridge:

```text
amount=1.00
currency=643
terminalId=12000679
receipt=9
rrn=625701637880
approved=false
message=Отказано
rc=99
```

`getLastTransaction()` после локального теста вернул тот же receipt=9, тот же RRN и тот же `rc=99`.

Это является важнейшим выводом диагностики: **повторяющийся текущий rc=99 не создаётся i-Retail UI, JL22, USB/AOA или нашим Kozen Payment Bridge.** Он возникает ниже нашего транспортного слоя — в SmartSkyPOS / конфигурации Kozen / TMS / банковском или эквайринговом контуре.

## 11. Последний read-only аудит эквайрингового контура

Последний аудит был полностью без финансовых команд.

Подтверждено:

- SmartSkyPOS находится в `state=0 / READY`;
- receipt 8 и 9 читаются из истории и оба имеют `approved=false / rc=99`;
- Kozen подключён по Wi-Fi и Android считает сеть валидированной;
- `185.162.94.67` доступен с Kozen по ICMP без потерь;
- DNS-имя `beta-tms.payment-guide.ru` разрешается в `91.142.87.36`, но ICMP-ответ от этого имени отсутствует;
- тест TCP `185.162.94.67:9221`, выполненный через `toybox nc -z`, **не является валидным результатом**, поскольку установленный `nc` на Kozen не поддерживает ключ `-z` и завершился сообщением `Unknown option 'z'`.

Следовательно, последний аудит не доказывает ни доступность, ни недоступность TCP/9221. С учётом решения получить отдельный тестовый контур этот вопрос переносится на следующий этап Kozen.

## 12. Текущий известный внешний блокер Kozen

Поставщик/эквайер должен предоставить отдельный тестовый контур Kozen.

После его получения требуется повторить минимальный приёмочный набор:

1. Проверить TMS/merchant/TID/profile.
2. Проверить `READY` и TerminalData.
3. Выполнить один локальный платёж 1 RUB непосредственно на Kozen.
4. Подтвердить `approved=true`.
5. Выполнить один платёж из основного i-Retail UI через JL22/AOA.
6. Сверить `requestId`, RRN, receipt и результат истории.
7. Проверить восстановление после обрыва без повторного списания.

До появления тестового контура дальнейшая отладка текущего `rc=99` внутри i-Retail нецелесообразна, поскольку локальный A/B-тест уже исключил наш транспорт и production bridge как источник этого кода.

## 13. Эксплуатационные режимы кофе-машины

Реализованы два режима.

### 13.1. `standalone`

Для отдельно стоящей кофе-машины:

- `i-Retail UI` автоматически запускается и остаётся главным интерфейсом;
- штатное приложение Jetinno продолжает работать в фоне;
- штатный хранитель экрана Jetinno не должен оставаться поверх i-Retail;
- foreground keeper возвращает i-Retail на передний план, если Jetinno пытается открыть заставку;
- Kozen real POS может быть включён через сохранённый параметр.

Проверено на реальном JL22: i-Retail возвращается поверх штатного Jetinno-интерфейса.

### 13.2. `kiosk`

Для кофе-машины в составе внешнего кофейного киоска:

- i-Retail не удерживает передний план;
- штатное Jetinno-приложение и его заставка могут оставаться главным локальным интерфейсом;
- режим сохраняется как эксплуатационная настройка.

## 15. Исправленные ошибки по ходу работ

В ходе интеграции были найдены и устранены несколько существенных ошибок:

1. Неверная интерпретация полей операции TerminalData: фактическая карточная операция имеет `type=00`, `transactionType=payment`.
2. Преждевременный тайм-аут AOA-клиента до открытия bridge.
3. Двойной запуск bridge-сервиса, который закрывал уже открытый accessory и вызывал `InterruptedIOException: read interrupted`.
4. Чтение `UsbAccessory.getSerial()` до выдачи USB permission на Android 11, вызывавшее `SecurityException`.
5. Аналогичная гонка двойного запуска в read-only recovery bridge.
6. Диагностический sentinel `Integer.MIN_VALUE` для отсутствующего `code`, который мог быть ошибочно воспринят как реальный банковский код.
7. Неправильный фильтр `logcat` в раннем `MAIN_22`, из-за которого предупреждение `PAYMENT_TX_ONCE` не попадало в отчёт.
8. Демонстрационная автопобеда POS-экрана по таймеру была удалена из реального карточного маршрута.
9. Добавлена защита от того, чтобы восстановленный старый `APPROVED` мог быть ошибочно применён к новому заказу.

## 16. Безопасностные инварианты, которые должны сохраниться дальше

Любые будущие изменения Kozen должны сохранять следующие правила:

- один `requestId` не вызывает более одного `payment()`;
- после `UNKNOWN` нет автоматического нового финансового вызова;
- перед продажей используются свежие `READY` и TerminalData;
- `code=0` не является финансовым одобрением;
- заказ считается оплаченным только при достоверном `approved=true`;
- повторный вход пользователя в экран оплаты не должен автоматически создавать вторую транзакцию;
- восстановление выполняется чтением состояния/истории, а не новой продажей;
- чувствительные карточные данные не журналируются;
- приготовление напитка не должно запускаться дважды из-за повторного callback/response;
- финансовый успех и успешная физическая выдача напитка остаются разными этапами заказа.

## 18. Точка продолжения проекта

Kozen теперь считается **архитектурно и программно интегрированным, с внешним банковским блокером на финальную приёмку**.

Следующее активное направление проекта — **Vendotek VT по протоколу VTK**.

Для Vendotek не следует переиспользовать Kozen Binder-протокол. Общим остаётся только внутренний платёжный контракт i-Retail и правила безопасной идемпотентности. Транспорт Vendotek и его двухфазная семантика `VRP -> выдача -> FIN` реализуются отдельным адаптером.
