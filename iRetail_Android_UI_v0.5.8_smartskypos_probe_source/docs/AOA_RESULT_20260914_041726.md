# JL22 ↔ Kozen P12: результат первого AOA-прогона

Исходный архив:

`test_reports/aoa/AOA_JL22_KOZEN_20260914_041726.zip`

## Подтверждено

AOA handshake полностью работает:

- JL22 находит Kozen как `0e8d:201c`;
- `AOA_GET_PROTOCOL` возвращает версию `2`;
- identification strings принимаются;
- `AOA_START` возвращает `0`;
- Kozen повторно перечисляется как `18d1:2d01`;
- JL22 открывает BULK IN `0x81` и BULK OUT `0x01`;
- Kozen переходит в `sys.usb.config=accessory,adb` / `sys.usb.state=accessory,adb`;
- Android на Kozen сохраняет `i-Retail Kozen Bridge` как обработчик аксессуара.

## PING/PONG

JL22 отправил `PING 1001` в AOA BULK канал в `04:08:31`.

Kozen Bridge был открыт пользователем/системой только в `04:13:39`, то есть примерно через 5 минут после первого AOA-перечисления. После открытия мост сразу прочитал ранее отправленный запрос:

```text
RX PING 1001
```

и успешно отправил ответ:

```text
TX PONG 1001 bridge=0.1.0 manufacturer=Kozen model=P12 android=11 sdk=30
```

Следовательно, двусторонний AOA-транспорт фактически подтверждён. Старый JL22-клиент завершил ожидание раньше, поэтому не успел принять PONG. Это ошибка тайм-аута диагностического клиента, а не USB/AOA транспорта.

## Исправление

В ветке `v0.5.14-smartskypos-over-aoa`:

- ожидание первого PONG увеличено до 8 минут без повторного засорения OUT endpoint;
- Kozen Bridge привязывается к локальному SmartSkyPOS Binder;
- добавлена безопасная команда `GET_STATE`, использующая только Binder transaction #1;
- финансовые команды по USB-протоколу по-прежнему отсутствуют.

Следующий критерий успеха:

```text
SMARTSKY_STATE_OVER_AOA_OK
```

с ответом вида:

```text
STATE 1003 code=0 state=0 bound=true descriptor=com.skytech.smartskyposlib.ISmartSkyPos
```
