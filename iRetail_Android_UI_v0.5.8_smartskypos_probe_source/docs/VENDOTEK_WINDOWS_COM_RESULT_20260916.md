# Vendotek VT — результат прямого Windows COM теста

Дата: 16.09.2026  
Архив: `VENDOTEK_COM_20260916_183749.zip`  
Ветка результата: `v0.5.28-vendotek-windows-com`

## Итог

Windows корректно увидел FTDI VCP терминала как `COM7`. Диагностический скрипт:

- нашёл `FTDI FT232R`, `VID:PID 0403:6001`;
- открыл `COM7`;
- установил `115200 8N1`, `Handshake=None`;
- успешно прошёл локальную самопроверку VTK CRC;
- сформировал корректный IDL-кадр.

Однако первая запись 34-байтового IDL-кадра в `System.IO.Ports.SerialPort` завершилась Windows-ошибкой:

```text
ERROR=Exception calling "Write" with "3" argument(s): "The write timed out."
```

Таким образом, прямой Windows COM путь пока **не подтверждён на уровне передачи байтов**, хотя COM-порт открывается.

## Важная изоляция

Это не ставит под сомнение сам Vendotek или VTK-транспорт на JL22: тот же физический FTDI-интерфейс на Android/Linux стабильно работает как `/dev/ttyUSB0`, и по нему уже подтверждены двусторонние `IDL` и `STATUS`.

Следовательно, текущая проблема локализована в Windows FTDI/VCP/COM слое либо его конкретной конфигурации, а не в формате VTK кадра.

## Безопасность

Финансовых команд не отправлялось. Запись зависла уже на первом не финансовом `IDL`, поэтому `STATUS`, `VRP`, `FIN`, `ABR`, `DIS` не передавались.

## Следующий шаг

В `v0.5.30-vendotek-windows-ftdi-audit` подготовлен полностью пассивный аудит Windows FTDI VCP. Он не пишет в COM ни одного байта и собирает:

- PnP Device ID;
- состояние устройства и ConfigManagerErrorCode;
- фактический `COMx`;
- `Win32_SerialPort`;
- FTDI driver provider/version/date/INF;
- `mode COMx`;
- значения CTS/DSR/CD после безопасного открытия порта;
- размеры входного/выходного буферов.

По этому результату можно будет решить, исправлять ли Windows VCP/драйвер либо оставить Windows COM только как вспомогательный путь, поскольку промышленный JL22→FTDI→Vendotek канал уже работает.
